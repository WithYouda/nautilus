# 浏览器间歇性刷新事故复盘

| 项目 | 内容 |
| --- | --- |
| 日期 | 2026-07-30 |
| 影响 | 用户正在使用 Nautilus 时，页面会在前端代码变化后热更新或整页刷新，打断当前操作 |
| 严重级别 | 高，属于运行方式错误，不是可接受的产品行为 |
| 状态 | 已修复并增加启动时防回归检查 |

## 1. 现象

用户通过标准交付地址 `http://<WSL2_IP>:5173` 使用应用时，浏览器会不定期刷新。刷新发生时可能丢失尚未提交的表单输入、当前编辑上下文和临时界面状态。

浏览器事件监控显示，页面加载了 `/@vite/client`，并建立了 Vite HMR WebSocket。应用代码本身没有定时调用 `location.reload()`；未修改源码的连续观察窗口中也没有发生额外导航。

## 2. 根因

`scripts/start.sh` 把 Vite 开发服务器作为标准产品运行服务器启动：

```text
vite --host 0.0.0.0 --port 5173
```

Vite 开发服务器会向页面注入 `/@vite/client`。当 Agent 修改 React、TypeScript、CSS 或相关依赖文件时，开发客户端会接收 HMR 更新；不能安全热替换的更新会触发整页 reload。因此用户感受到的是“时不时刷新”，实际触发条件是工作区源码发生变化。

本次问题不是 React `StrictMode`、授权状态轮询、计时 WebSocket或后端健康检查导致的。错误在于把开发态服务当成了稳定交付运行态。

## 3. 为什么之前没有发现

1. 浏览器验证只检查了页面能否打开、写操作是否成功、是否横向溢出和是否存在控制台错误，没有验证页面是否加载 HMR 客户端。
2. 验证时间较短，并且通常在代码修改完成后进行，没有在浏览器打开期间再次修改源码来观察导航事件。
3. `start.sh` 同时承担开发启动和用户交付，没有明确区分 `dev` 与稳定运行模式。
4. 交付检查只确认端口、健康接口和构建成功，没有检查实际 5173 响应来自开发服务器还是生产构建。

## 4. 修复

1. `scripts/start.sh` 启动前执行前端生产构建。
2. 标准 5173 服务改为 `vite preview`，只提供构建后的静态资源，不注入 HMR 客户端。
3. `vite.config.ts` 为 preview 单独配置 API 和 WebSocket 代理。
4. 启动脚本读取首页响应；若发现 `/@vite/client`，立即拒绝启动并提示运行模式错误。
5. `npm run dev` 保留给开发者使用，但不得作为用户交付地址的启动方式。

## 5. 防复发规则

以后所有 Web 交付必须执行以下检查：

1. 标准启动脚本不得直接运行 Vite、Webpack 等开发服务器。
2. 用户使用的页面响应中不得包含 `/@vite/client`、React Refresh 或其他开发热更新客户端。
3. 浏览器验收需要监听 `Page.frameNavigated`；在观察窗口中除测试主动触发外，导航次数必须为零。
4. 前端源码修改和用户验收不得共用同一个 HMR 页面。开发端口与稳定交付端口必须有清晰边界。
5. 启动脚本必须在构建失败、前端未就绪或检测到开发客户端时失败退出，不能继续打印“已启动”。
6. 每次修改启动方式后，至少验证 API 代理、计时 WebSocket、授权状态和页面无自动导航。

## 6. 代码审查提示

看到以下任一情况时，必须阻止作为产品运行方式合入：

- `start.sh`、服务管理配置或交付文档直接执行 `vite`、`npm run dev`。
- 交付页面源代码包含 `/@vite/client`。
- 用户端口存在 HMR WebSocket。
- 只验证 `npm run build` 成功，却仍用开发服务器交付。

核心教训：构建成功不等于用户正在使用生产构建。必须验证实际监听交付端口的进程和页面内容。
