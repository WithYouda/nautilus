## 0. 文档目的与使用规则

本文件用于保存 Nautilus 产品讨论中已经形成的、对后续设计有约束力的结论，避免上下文压缩、窗口切换或 Agent 交接后重复询问已经确认的问题。

后续每次产生重要产品或技术结论时，必须：

1. 先说明本轮推进的单一决策是什么。
2. 明确区分用户偏好、产品要求、技术建议和开放问题。
3. 用户确认后，将结论追加到本文件，并在“更新记录”中注明日期。
4. 同时更新 `docs/progress/nautilus-development-status.md` 的实际状态和下一项任务。
5. 不把讨论中的未来能力写成已经实现的功能，不把 AI 推测写成事实。
6. 落实上一项确认后，在同轮直接提出下一项具体建议，不再单独询问是否继续；新建议仍须用户确认后才写入 PRD。

本文件的状态标记：

- **已确认**：用户已经明确同意，后续设计必须遵守，除非提出新证据并重新讨论。
- **推荐方向**：基于当前事实的技术或产品建议，尚未被用户单独确认。
- **待讨论**：尚未形成结论，不能在后续回复中假设已经决定。
- **当前实现**：代码中已经存在并经过测试的能力；详细事实仍以开发进度文档和正式规格为准。
- **明确不做/暂缓**：当前阶段不进入实现范围。

本轮特别修正：此前已经确认“陌生领域中的学习契约必须有来源、可信等级和探索模式”后，不应再次把它作为待确认问题。今后不得重复询问已确认结论。

## 1. 产品北极星

### 1.1 已确认定位

Nautilus 是一个**长期学习协作者**，主要责任不是单次回答问题，而是持续维护以下三者的一致性：

```text
用户真正想达到的学习结果
    <-> 用户当前真实状态
    <-> 下一步最值得做的行动
```

产品的核心承诺可以表述为：

> 用户每次回来时，Nautilus 都能说明用户走到哪里、什么已经被证据支持、什么仍然未知，以及下一步最值得做什么。

Nautilus 不是以下产品的简单相加：

- 只会讲题的 AI 导师；
- 只负责排期的 Todo 或项目管理器；
- 只负责重复记忆的背卡软件；
- 只保存聊天记录的聊天机器人；
- 只会一次性生成路线的计划生成器。

### 1.2 核心问题

长期学习最难的部分不是“生成一个看起来完整的计划”，而是：

- 用户的目标经常含糊、范围会变化；
- 用户的真实可用时间和学习速度事先未知；
- 任务完成不等于能力形成；
- 学习证据可能延迟出现；
- 用户中断后很难恢复上下文和节奏；
- AI 容易把猜测、用户自报和客观事实混在一起。

因此 Nautilus 的真正差异化方向是**状态可信度和长期连续性**，而不是“回答更像老师”或“计划排得更漂亮”。

### 1.3 产品价值判断

真正有价值的体验不是：

> AI 给我一份完美的未来计划。

而是：

> AI 先承认未知，用低成本行动获得信号，然后逐步把计划、节奏和学习判断变得可信。

### 1.4 用户定位状态

Nautilus 的服务对象不再按考试、学科、职业身份或具体知识领域排序，而是：**任何希望在深度学习过程中获得持续帮助的用户**。考研/考公/考证、高校学习、自学编程、职业转型、长期专业学习和多个目标并行管理，都是可以承载这一承诺的具体场景，不构成彼此排他的首批用户层级。

这里的“任何用户”仍受“深度学习”边界约束：Nautilus 重点解决需要持续理解、实践、产出、证据验证、复盘和路线调整的学习问题，不因扩大服务对象而承诺覆盖一次性问答、轻量打卡、机构教学管理或所有教育产品场景。

当前产品设计的第一位真实用户是产品作者本人。以自身长期使用来发现问题、验证连续性和判断是否真正有帮助，是当前阶段的主要产品反馈来源；这不等同于已经证明其他用户也有相同需求。

### 1.5 终局形态优先的讨论范围（已确认）

当前产品讨论以 Nautilus 的长期终局形态为对象，不因为实现阶段、当前代码规模或 MVP 成本而提前否定有价值的想法。复杂度本身不是问题，真正需要控制的是概念之间是否自洽、用户是否能够理解、权限和事实边界是否清楚。

产品愿景、规范架构和具体落地顺序分开管理：讨论阶段可以先完整设计终局能力，未来实现时再决定先后顺序，但不能因为某项能力尚未实现就把它写成当前已有功能。

旧 UI、旧 API 和旧固定层级不构成未来产品的兼容约束，允许直接推倒重做；但用户数据、默认数据库和历史证据仍然受备份、校验、恢复和授权规则保护。允许破坏性重构，不等于允许无保护地删除学习历史。

## 2. 当前实现与未来愿景的边界

### 2.1 当前已经实现的产品基础

当前代码已经具备：

- 学习计划、科目、主题、任务四层结构；
- 全部计划总览、单计划概览/结构/排期；
- 任务新增、编辑、排序、软删除和可逆完成；
- 服务端稳定计算计划“下一项”任务；
- 任务计时与学习会话记录；
- `global / plan / task / independent` 对话范围；
- Provider Profile、Provider Model、多模型、OpenAI-compatible provider；
- 模型发现、手动模型、Chat Run、SSE、断线恢复和配置快照；
- 对话历史、标题生成、改名、软删除和删除后恢复；
- 全局、计划、任务 AI 入口；
- 本地优先、API Key 脱敏和隔离测试流程；
- 密集、稳定、适合长期使用的工作区与学习室布局。

这些是目前可以基于代码和测试说明的事实，但它们还不等于完整的长期学习协作者。

### 2.2 尚未实现的核心愿景

以下仍属于产品设计或后续工程方向：

- 学习成果和掌握度模型；
- 事实、观察、推断、决定的事件账本；
- 学习证据和跨时间延迟验证；
- 轻量学习成果知识图谱；
- 领域知识包与来源核验；
- 学习委托、学习契约和角色交接协议；
- 受 Runtime 约束的 Agent 工具环境；
- 主动学习教练和计划分析工作流；
- 自适应时间模型；
- 资料导入、知识库和正式研究流程。

## 3. 可信核心与信息分层

### 3.1 已确认：Nautilus Core 的职责

AI 不能直接成为事实数据库的写入者。Nautilus Core 负责：

- 计划、任务和学习对象的领域语义；
- 学习事实事件；
- 任务执行状态；
- 学习状态计算；
- 权限、审批和状态转换；
- 时间和计时基础约束；
- 审计、回放和撤销；
- 对 Agent 提交的观察、证据和变更草案进行结构校验。

AI 可以提交结构化的观察、证据、命令或变更草案，但不能绕过领域服务直接修改事实、正式计划或数据库。

### 3.2 四类信息

所有长期状态都必须区分：

```text
事实 Fact：系统或用户实际产生的事件
观察 Observation：基于具体证据的 AI 观察
推断 Inference：AI 对现状的解释或概率性判断
决定 Decision：用户确认的计划、标准或长期变化
```

AI 的自然语言回答不能自动成为事实。推断也不能自动升级为决定。

### 3.3 执行状态与学习状态分离

任务做没做和能力是否形成是两个维度：

```text
执行状态：未开始、进行中、已完成、已撤销
学习状态：未观察、证据不足、有支持证据、反面证据、需要补强、等待回访、证据过期
```

例如：

```text
任务执行：已完成
学习委托：已关闭
学习成果：有初步支持证据，等待迁移或延迟验证
```

这三种状态同时存在并不矛盾。

### 3.4 事件账本方向

推荐采用“现有关系型业务表 + 追加式事件账本”的混合方案，而不是立即把全部系统改造成全量 Event Sourcing。

事件类别包括：

- 用户意图；
- 计划和任务变更；
- 学习会话、计时和任务执行；
- 原始学习产出；
- AI 观察和证据引用；
- 用户确认的决定。

派生的进度、学习状态、回访队列和建议应当可以根据事件重新计算。缓存、搜索索引和 AI 中间结果不能成为唯一数据源。

## 4. 学习证据与真实状态

### 4.1 核心判断

Nautilus 不能只依靠：

- 用户说“我会了”；
- AI 觉得用户回答流畅；
- 用户完成了一个任务勾选；
- 一次题目答对；
- 一段代码能够运行。

这些信号都可能有价值，但单独不足以证明稳定能力。

### 4.2 证据来源

证据可以来自：

- 用户主动提交的笔记、代码、推导、作品或外部成绩；
- 任务 Agent 观察到的独立回答和操作过程；
- AI 生成的练习、变式问题和迁移问题；
- 沙箱测试、代码测试、实验运行结果和性能基准；
- 跨时间回忆和复习结果；
- 用户在新情境中独立使用知识的产出；
- 用户声明完成，但必须明确标为“用户声明”，不能伪装成独立验证。

AI 出题问答和用户主动提供产出都可以使用，但它们不是二选一，也不能由 AI 单独决定证据是否充分。应根据学习成果类型选择最低成本的证据组合。

### 4.3 证据的时间性质

学习证据有即时证据和延迟证据：

- 即时：刚学完的解释、实验、练习和产出；
- 延迟：隔一段时间后的回忆、变式和迁移。

延迟验证不应阻塞用户继续前进，但在验证完成前，学习状态必须保持“等待回访”或“证据不足”，不能伪装成稳定掌握。

### 4.4 遗忘曲线与间隔验证

可以借鉴艾宾浩斯遗忘曲线所代表的核心思想：记忆会衰减，跨时间的主动回忆比刚学完的重复确认更有价值。但不能把某一条固定曲线或单一公式直接当成每个人的真实记忆模型。

Nautilus 应把它实现为**证据到期与间隔回访机制**，而不是复制背单词软件的固定卡片曲线：

- 根据成果重要性、最近证据、错误记录和用户实际回忆结果安排下一次回访；
- 先使用保守的初始间隔，随后根据真实回忆、变式和迁移表现调整；
- 回访任务可以很短，并与新的学习任务并行，不因等待验证而阻塞路线；
- 回访失败会产生反面证据或补强建议，而不是简单把所有进度清零；
- 系统展示的是“何时需要再次验证、为什么”，不是伪装成精确的个人遗忘概率；
- 不能因为采用了间隔复习就声称已经可靠测得掌握度。

因此，遗忘曲线是调度启发和产品原则，不是掌握结论本身。

### 4.5 个人证据覆盖层

知识图谱表示“应该能够做什么”，证据覆盖层表示“当前有什么证据支持或反驳这些能力”。一个成果节点可能同时拥有：

```text
支持证据
反面证据
尚未验证的维度
来源和时间
证据可信等级
```

## 5. 轻量学习成果知识图谱

### 5.1 已确认方向

Nautilus 需要知识图谱，但第一版不是百科图谱，也不是试图覆盖所有世界知识，而是：

> **轻量学习成果图谱 + 个人证据覆盖层。**

它与计划树分工不同：

```text
计划树：用户要做什么
成果图谱：用户最终要能够做什么
证据覆盖：用户目前有什么支持或反面证据
```

### 5.2 第一版关系

第一版优先支持少量、可审计关系：

- `prerequisite_of`：某成果是另一成果的前置；
- `task_supports_outcome`：任务支持形成某成果；
- `evidence_supports_outcome`：证据支持某成果；
- `evidence_contradicts_outcome`：证据反驳或削弱某成果判断。

关键关系不能只因为 AI 生成就变成硬前置。它需要领域知识包、外部来源或明确实践依据。

### 5.3 领域知识包

领域知识包是声明式、可审查、可版本化的数据，不包含任意可执行代码。它可以声明：

- 成果节点；
- 前置关系；
- 规范、解释和验证来源；
- 适用范围；
- 版本和更新时间；
- 争议、限制和未知部分。

用户可以确认“这是否符合自己的目标”，但用户的确认不能证明陌生领域关系在客观上正确。AI 推断最多是临时假设。

### 5.3.1 首个领域知识包策略（已确认）

首个领域知识包采用**窄领域示范包**，优先选择来源稳定、关系可审查、验证方式明确且能够清楚声明适用范围与限制的领域，不以一开始覆盖通用知识为目标。包外的 AI 推断仍只能作为临时假设，不能冒充领域标准或硬前置；知识包版本更新必须保留旧版本、争议和未知，不得静默改写既有证据归属。

这项策略只确认首个知识包的范围方法和质量门槛，不提前决定具体领域名称，也不把能力插件、资料库或 Web Search 扩展混入知识包本身。

### 5.4 能力插件

需要执行环境的能力放入插件或受控服务，例如：

- Python 或代码测试沙箱；
- 文档解析；
- Web Search；
- 性能基准；
- 日历；
- 题目验证；
- 外部服务连接。

知识包负责“领域上声明什么”，插件负责“用什么工具验证或执行”。二者不能混为一个可以任意执行的知识文件。

能力插件不为任务 Agent 创建另一套运行模式。所有工具都由统一 Agent Runtime 按当前角色契约、数据范围、显式授权、沙箱和资源限制装配；工程上先接入代码测试、题目验证还是文档解析，只取决于首个实施切片要验证什么，不构成新的终局产品架构决策。

## 6. 目标、计划、任务和学习委托

### 6.1 当前代码语义

当前数据库实体是：

```text
learning_goal -> subject -> topic -> task
```

界面将 `learning_goal` 统一称为“计划”。这是当前实现事实，不等于最终产品词汇已经永久定稿。

### 6.2 目标与计划的语义分离（已确认）

长期产品语义倾向于：

```text
目标：用户想达到的结果
计划：实现目标的路线和组织方式
任务：用户要执行的具体行动
```

目标与计划在领域语义上分离，但用户界面采用渐进披露。目标回答“为什么学、最终想得到什么结果”，计划回答“当前采用哪条路线、什么时间安排和哪些组织方式”。同一目标可以关联多个计划；计划结束不等于目标完成，学习成果仍是独立的长期能力对象。

- 日常入口仍以计划和任务为主，不要求用户每次先维护独立目标对象。
- 单计划场景可以把目标作为可编辑的学习方向或期望结果呈现，不增加额外的强制表单层。
- 当出现多个计划、路线切换、长期回顾或跨计划成果时，显式展示目标中心和目标与计划的关联。
- 没有稳定目标的计划可以先开始，之后再建立或调整目标关联；目标在稳定前保持低承诺、可编辑和可撤销。
- 目标、综合成果和计划不能互相冒充：目标表达意图，成果表达可验证能力，计划表达当前路线与组织。

### 6.3 学习委托不是任务本身

已确认采用以下层级：

```text
计划任务 Task
  -> 学习委托 Assignment
    -> 学习会话 Session
      -> 证据 Evidence / 观察 Observation
```

- **任务**是用户看得懂的长期计划节点，例如“学习 KV Cache”。
- **学习委托**是围绕任务的一份长期工作单，记录本次要验证什么、时间预算、学习模式、允许工具和停止条件。
- **学习会话**记录真实发生的一次或多次学习过程。
- **证据/观察**记录实际产出、回答、实验、错误、未知和支持程度。

一个学习委托可以有多次会话：

```text
第一次：理解原理
第二次：完成实验
第三次：延迟回忆
第四次：迁移验证
```

同一委托可以包含多次会话、复习、重试、延迟验证和契约版本更新；是否建立新委托依据独立学习承诺判断，不把每次复习都伪装成新任务。

### 6.3.1 委托并行与新建条件（已确认）

此前提出“同一任务同时最多一个执行中委托”和“只有完成标准发生实质变化才新建委托”，是为了降低第一版状态和交互复杂度的推荐约束，不是已经确认的产品规则。用户提出质疑后，这两个限制暂不成立。

更有弹性的候选方向是：

- 数据层允许同一任务拥有多个同时进行中的学习委托；
- 界面层只突出一个“当前焦点”，不把它误解为系统中只能存在一个活动委托；
- Core/Runtime 检查委托之间的范围重叠、证据冲突、工具冲突和时间冲突；
- 学习教练可以推荐下一项，但不能因为推荐焦点而暂停或关闭其他委托；
- 并行委托的创建、接受、暂停和关闭仍需要用户可见、可确认的状态变化。

“完成标准是否变化”也不应是创建新委托的唯一条件。可以继续使用同一委托的情况包括：同一目标、同一范围下的多次会话、复习、重试、延迟验证和不同练习样本。更适合创建新委托的情况还包括：

- 用户开启一个独立的工作包或学习分支；
- 目标结果、范围、责任边界或资源环境明显不同；
- 需要独立的时间承诺、隐私范围、工具权限或 Agent 角色；
- 用户希望保留两条互不覆盖的路线，分别观察效果；
- 原委托已暂停或关闭，用户开始一项新的阶段性工作。

如果只是完成标准的小幅调整，可以创建新的契约版本并保留在同一委托内；如果调整使原委托的目的、范围或责任发生不兼容变化，则应关闭/替代旧委托并建立新的委托，而不能静默覆盖旧历史。

该模型已确认。Nautilus 允许用户围绕同一任务维护多个开放的独立学习委托，但默认只运行一个实际学习会话；“当前焦点”只是界面和推荐层的突出对象，不代表其他委托被暂停或失效。

并行委托的新建条件采用“独立工作承诺”原则，而不是只看完成标准是否变化。以下情况可以继续留在同一委托中：同一目标和范围下的多次会话、复习、重试、延迟验证、不同练习样本，以及小幅契约版本更新。以下情况适合建立新的委托：独立工作包或学习分支、目标/范围/责任边界不兼容、不同时间承诺/隐私范围/工具权限/Agent 角色、用户希望比较两条路线，或原委托关闭后重新开始新的阶段性工作。

### 6.3.2 委托候选的成本受控检测（原则已确认，具体阈值待设计）

用户确认系统不能对每条消息、每次计时更新或每个细小学习事件调用模型检测新委托，否则成本和打扰都不可控。委托候选检测采用**事件门控 + 会话边界 + 批量复盘**，而不是持续语义监控。

推荐分为四层：

1. **持续的低成本信号记录，不调用额外模型**。Core 记录用户明确提出“单独学习/稍后安排”、工具或权限变化、反复失败、范围变化、产出提交和契约冲突等结构化事件。
2. **复用当前 Agent 运行**。任务 Agent 本来就在回答或执行时，可以随结果附带可选的 `assignment_signal`，不再为了检测单独发起第二次模型调用。普通提问、一次小错误或临时插曲默认不产生正式候选。
3. **会话边界做主要自动判断**。用户暂停/结束会话、切换任务、提交阶段产出或准备关闭委托时，将尚未分析的信号去重后批量判断一次。浏览器异常关闭或超时只标记“待复盘”，不在后台立即产生模型费用。
4. **计划级批量复盘**。只有存在未处理信号、跨会话重复阻塞、路线漂移或用户主动请求时，学习教练/计划 Agent 才在日复盘、周复盘或下次打开计划时合并分析；没有新增有效信号时跳过调用。

即时打断只适用于：

- 用户明确要求把某件事单独安排；
- 当前委托已经无法继续；
- 继续会明显浪费时间或使已确认范围失效；
- 新方向需要额外费用、外部数据、不同权限或高风险工具；
- 必须先由用户决定是否改变当前学习承诺。

其他非阻塞信号先进入候选队列，在自然停顿或会话结束时以简短方式呈现，不能在学习过程中频繁弹窗。正式创建仍需用户确认；创建后默认进入待开始，不自动抢占当前焦点。

成本控制应遵守：

- 同一批未处理事件只分析一次，使用稳定事件 ID 去重；
- 优先传递结构化摘要和引用，不重复发送完整对话；
- 一次分析可以合并多个候选，不能按候选逐条调用模型；
- 专用检测器应有会话/日级预算和冷却时间，具体默认值在真实成本测试后确定；
- 用户可以关闭主动检测、降低频率或只保留手动建议；
- 高成本深度分析只在用户请求、重要范围变化或低成本判断无法确定时启用。

### 6.3.3 委托生命周期、当前焦点与学习会话（已确认）

学习委托需要拆成三个彼此独立的维度，不能用一个状态字段同时表示“是否被用户接受”“现在是否优先处理”和“用户此刻是否正在学习”：

```text
委托生命周期：这份长期工作单是否仍然开放
当前焦点：界面和推荐层现在优先突出哪一份工作单
学习会话：用户此刻实际进行的学习过程
```

委托生命周期为：

```text
待开始 -> 推进中 -> 已暂停 -> 已结束 / 已取消
```

- **待开始**：用户已经确认创建，但还没有开始第一次会话；不计入实际学习时间，也不默认触发提醒。
- **推进中**：委托已被用户接受，后续可以继续安排会话；可以同时存在多个“推进中”委托，但它们不代表同时有多个计时器。
- **已暂停**：用户明确暂时不继续；历史会话、产出和证据保留，默认不进入下一项推荐。
- **已结束**：用户确认这份工作单结束。结束原因和结果另行记录，例如达到约定、部分完成或未完成，不把“已结束”直接等同于“已经掌握”。
- **已取消**：用户决定不再推进；保留历史记录，不再作为当前路线的开放工作。

AI 自动发现的“可能需要单独安排”只是一条候选建议，不是委托生命周期中的“草稿”。候选在用户确认前不占用活动委托数量、不参与进度、不触发复习或督学提醒。用户确认后才创建正式委托并进入“待开始”。

当前焦点是独立指针：同一时间最多一个。用户可以手动切换；系统可以根据截止时间、阻塞、复习到期和用户偏好推荐，但不能因为推荐而暂停、关闭或静默切换其他委托。当前焦点改变不等于创建会话，选择“稍后处理”也不会开始计时。

学习会话单独使用自己的状态，例如“未开始、学习中、已暂停、已结束、异常中断”。默认同一时间只允许一个“学习中”会话；“学习中”只表示此刻实际执行的会话，不表示委托是唯一开放的工作。

基本转换规则：

```text
候选建议 --用户确认--> 待开始
待开始 --用户选择开始/实际开启会话--> 推进中
推进中 --用户确认暂停--> 已暂停
已暂停 --用户恢复--> 推进中
推进中/已暂停 --用户确认结束--> 已结束
待开始/推进中/已暂停 --用户确认取消--> 已取消
```

AI 可以提出暂停、结束、拆分或继续的建议；Core 只负责校验事实和执行用户确认的状态命令。关闭委托不代表学习成果已经获得支持，掌握状态仍由证据和延迟验证单独计算。

### 6.3.4 并行委托关联与冲突的分级处理（已确认）

多个委托同时开放时，不能把所有重叠都当成冲突，也不能让 AI 自己替用户裁决。系统应先判断它们是否只是可以协同的关联，再根据**确定性**和**实际影响**决定是否提示、请求选择或阻断。AI 可以发现潜在关联、解释影响和提出方案；Core 负责验证固定时间、单会话、权限、资源互斥和事实写入等确定性约束。

内部判断至少包含两个维度：

```text
确定性：预测 / 已确认
影响：不影响继续 / 需要取舍 / 无法或不应继续
```

预计时长、未来负载和可能的路线竞争通常只是预测，不能因为看起来严重就伪装成确定事实。提示应尽量推迟到最接近实际决策的时刻，例如安排日程、准备开始会话或临近硬截止日期；已经存在活动学习会话、权限缺失或独占资源被占用等确定事实则在具体操作发生时立即处理。

面向处理结果采用以下三级：

```text
信息提示：存在关系或资源重叠，但不影响继续
软冲突：可能争夺时间、焦点或相同产出，提示用户选择处理方式
硬阻断：当前操作在事实、权限或资源上不能同时成立，必须先处理冲突
```

**信息提示**更准确地说是“关联”：两个委托支持同一个学习成果、引用同一资料，或者一个委托的证据可能帮助另一个委托。系统应优先寻找资料、成果和证据引用能否复用，只在详情或复盘中说明，不打断学习，也不要求用户合并。

**软冲突**的例子：两个委托都安排在同一时间段；都被标记为高优先级；都需要用户完成相似产出；两个路线都想成为当前焦点。系统应说明冲突和取舍，提供“保留并行、暂缓一个、合并为同一工作、调整时间”等用户动作。用户可以选择继续，不由 AI 静默暂停任何委托。

**硬阻断**只用于确定性的不可能或不安全情况：已经存在一个进行中的学习会话时，不能再启动第二个实际计时会话；两个委托要求互斥的独占工具/设备或不同的高风险权限；一次操作会把同一份产出同时写成两个互相冲突的事实；用户尚未授权所需的外部费用、私密资料或危险工具。阻断只阻止具体操作，不关闭或删除相关委托。

时间估计冲突默认属于软冲突，因为学习时长本身带有不确定性；只有固定日程、硬截止日期或用户明确设置的不可移动约束，才可能升级为需要确认的冲突。系统应优先给出可执行的调整建议，而不是声称已经证明用户无法完成全部委托。

用户可以在冲突提示中选择“暂不处理”。这会保留冲突事件，避免每次重复提示；当冲突影响即将开始的会话、固定截止日期或权限操作时再重新提醒。所有自动分级和用户选择都应写入事件记录，以便复盘和撤销。

总体原则是偏向用户自主和并行探索。计划中存在分支和竞争方向本身不是错误；Nautilus 的责任是让用户理解代价和约束，而不是为了结构整齐自动暂停、合并或关闭委托。

### 6.4 交接包与学习委托的区别

学习委托是长期状态对象；交接包是角色切换时生成的、带版本的上下文快照。交接包不取代委托，也不承担全部历史。

```text
学习教练创建委托
  -> 生成交接包 v1
  -> 启动任务会话
  -> Core 接收结果并更新委托
  -> 下一次验证生成交接包 v2
```

## 7. 学习契约与完成标准

### 7.1 已确认：先建立学习契约，再执行

学习委托开始执行前，必须形成一份版本化的学习契约，至少包含：

- 本次要形成的能力；
- 可观察行为；
- 最低证据要求；
- 验证方式；
- 标准来源、来源类型和可信等级；
- 哪些情况只能算部分完成；
- 是否需要延迟验证；
- 本次时间预算和停止条件；
- 契约版本。

任务 Agent 可以提出契约草案，但不能在执行中无声地提高或降低门槛。契约变更必须生成新版本，旧会话和证据继续保留。

### 7.2 不同成果类型的证据配方

不使用一套万能评分表，而按成果类型采用最低成本的证据配方：

概念理解：

```text
用自己的话解释
+ 区分相近概念或指出常见误解
+ 一个变式问题
```

程序或操作：

```text
独立执行
+ 可运行产出或测试结果
+ 对关键步骤和取舍的解释
```

记忆类：

```text
不看资料回忆
+ 延迟回忆
+ 在新题目中使用
```

项目产出：

```text
可检查的作品
+ 明确验收标准
+ 用户说明设计取舍
+ 必要时外部测试或评审
```

任务重要程度、错误代价和用户时间预算会影响证据要求；探索性小任务可以采用较低成本的契约。

### 7.3 陌生领域的标准来源

用户不懂领域时，用户只能确认自己的目标和取舍，不能负责证明领域标准正确。学习契约必须标明标准来源：

- **规范来源**：官方文档、考试大纲、技术标准、论文原文、项目源码；回答应该学什么或系统如何工作。
- **解释来源**：教材、课程和高质量讲解；帮助理解，但不必单独成为最终判定依据。
- **实践验证来源**：测试套件、代码运行、性能基准和项目验收标准；回答能否用于实际任务。
- **AI 临时假设**：尚未充分核验的候选拆解，只能指导探测，不能成为硬前置或掌握结论。

## 8. “完成”的分层确认

### 8.1 三种完成

“完成”不是单一状态，必须分成：

1. **执行完成**：客观活动是否发生，例如计时结束、产出提交、测试执行。
2. **学习委托关闭**：本次工作单是否完成了预先约定的活动和最低产出。
3. **学习成果获得支持**：是否有足够证据支持用户形成了目标能力。

### 8.2 提出权和确认权

可以提出“完成”的角色：

- 用户：主动声明或手动结束；
- 任务 Agent：根据契约和会话结果提出建议；
- 学习教练：根据连续性和状态提醒可以结束或需要补验证；
- Core：根据确定性事件确认机械事实。

确认权按状态分层：

- Core 可以确认计时、提交、测试、会话等客观事实；
- 用户可以确认本次学习委托关闭；系统必须记录这是用户确认还是 AI 建议；
- AI 可以给出证据解释和“建议标记为有支持证据”；
- AI 不能只根据语言流畅度单独把“已掌握”写入事实状态；
- 学习成果通过证据组合、迁移和延迟验证逐步获得支持。

用户可以声明结束学习、不再验证；系统记录“用户声明”和“独立验证未完成”。按 2026-09-14/16 确认规则，这不等于新领域学习行动验证完成，也不得绕过验证自动写入 action.completed；旧计划的记录型入口保留原有边界。

### 8.3 推荐状态

```text
委托：待开始 -> 推进中 -> 已暂停 -> 已结束 / 已取消
学习会话：未开始 -> 学习中 -> 已暂停 -> 已结束 / 异常中断
学习成果：未观察 -> 证据不足 -> 有支持证据
          -> 需要补强 -> 等待回访 -> 证据过期
```

此前“执行中 -> 待确认 -> 已关闭”的简化委托状态仅为早期草案，已由 6.3.3 的生命周期取代，不再作为规范。

AI 的权限是提出、解释依据、列出缺口和安排验证，不是把模型置信度当作事实授权。

## 9. Agent Runtime、人格与学习模式

### 9.1 一个 Runtime，多种角色

Nautilus 采用一套 Agent Runtime，不创建三套完全独立的 AI 系统。不同角色由 Profile、角色契约、上下文、工具和策略组合而成。

完整运行时结构为：

```text
人格 Profile：它是谁、如何说话
  -> 角色契约：当前负责什么
    -> Runtime 上下文与权限：能看到什么、能做什么
      -> 学习模式：采用什么方法教学
```

人格 Profile 可以由用户自由编辑，但不能改变事实、权限、时间、证据和审批规则。

### 9.2 Persona Profile（人格档案）

用户提供的自然语言人格描述可以很开放，例如：

> 你是一个严格、直接、不会羞辱人的学习教练，发现我拖延时要指出问题，但也要给出可执行的恢复办法。

系统将原文编译为结构化配置，但必须：

- 保存原始文本；
- Schema 校验；
- 检测冲突和越权倾向；
- 提供预览和用户确认；
- 支持版本、回滚和启用/停用；
- 将表达风格与权限、事实写入、工具调用严格分离。

督学和任务 Agent 可以共享同一个人格 Profile，保持称呼、语气、督促强度和角色连续性；但它们不共享完整系统提示词、数据范围和工具权限。

### 9.3 内置与可共享

学习教练作为系统内置角色更符合用户直觉；人格 Profile 和学习模式仍应设计为声明式、可导入导出的数据包，未来可以共享和形成社区。

需要执行工具的部分才是插件。人格不是插件代码，也不应因为导入人格包而获得新权限。

### 9.4 学习模式

学习模式决定“怎么教”，与人格决定“怎么说”不同。初步内置模式包括：

- 直接讲解；
- 苏格拉底探究；
- 练习优先；
- 费曼复述；
- 项目实践；
- 个人自适应模式。

用户可以手动创建模式，也可以由 AI 根据长期互动总结并沉淀为用户自定义模式。自定义模式需要保留原始描述、结构化配置、版本和回滚能力。

默认模式不是永远固定的系统模板。新用户先从一套保守的系统基线开始，随着真实互动、证据和用户反馈积累，AI 可以提出个人学习模式修订草案；用户确认后，它成为当前个人默认模式。系统也可以在具体任务中后台选择更合适的内置或个人模式，但不能因为临时切换就覆盖用户的长期默认配置。

学习模式可以在后台根据任务、证据和用户反馈自动切换，界面只需要提供非侵入式提示；具体图标和颜色留到统一视觉风格阶段决定。

### 9.5 苏格拉底模式是协议，不是 Prompt

苏格拉底模式采用运行时控制的提示阶梯：

```text
H0 开放问题
H1 提醒相关概念
H2 缩小问题范围
H3 给局部结构或示例
H4 直接解释
```

流程：绑定成果 -> 用户尝试 -> 按阶梯推进 -> 必要时解释 -> 变式/迁移验证 -> 提交观察。

用户明确要求直接答案，或连续无法推进时，可以升级提示；切换在安全回合边界发生，不能来回抖动。真正的阶梯、计数、切换条件和权限由 Runtime 执行，不能只依赖 Prompt。

### 9.6 模型策略与思考强度（边界已确认，映射待设计）

模型能力和本次运行投入是两个不同维度，不能用提高思考强度把弱模型伪装成强模型：

```text
模型策略：主要决定使用哪个能力层级、上下文能力和工具能力
思考强度：调节当前一次运行可投入的推理、输出和验证资源
```

用户自行选择模型策略。Nautilus 可以根据当前任务的复杂度、风险、工具需求或证据矛盾提出“是否升级模型”的建议，但不能未经用户同意自动切换模型、Provider 或策略。用户可以关闭主动升级建议；关闭后不再收到主动升级提示，但确定性的能力缺失或运行失败仍应如实说明。

模型切换不改变 Agent 的角色权限、Core 的事实约束或审批边界。人格 Profile、学习模式、模型策略和工具权限分别管理，不能因为选择更强模型而扩大数据读取或写入能力。

推荐的后续实现方向（尚未确认，也尚未实现）：默认提供节省、平衡、深度等策略，策略内部映射到用户已配置并授权的模型候选；对话中允许用户覆盖当前模型或思考强度。每次 Chat Run 都冻结实际使用的 Provider、模型、策略和资源参数，运行中修改只作用于下一次发送或重新生成。若模型不支持原生思考强度参数，Runtime 不应靠 Prompt 假装支持，而应明确降级或使用受控的运行预算映射。

### 9.7 模型策略的作用域与继承（作用域已确认，细节待设计）

用户可以在以下层级逐级覆盖模型策略：

```text
全局默认
  -> 计划
    -> 任务
      -> 单次对话
        -> 本次运行快照
```

这表示用户可以让大多数学习工作使用一个默认策略，再为某个计划、某个任务或某次对话指定不同策略。未被当前层级明确设置的字段继续继承上一级；本次运行实际采用的配置必须冻结并可追溯。模型策略覆盖不能扩大 Agent 的数据范围、工具权限或事实写入权限。

推荐的后续交互细节（尚未确认）：每个层级都提供“继承上级”状态；界面显示当前生效值及其来源；单次对话的覆盖优先于计划和任务设置，但不会反向修改它们。用户切换 Provider 或模型时，应同时看到隐私、能力、费用和延迟影响。

### 9.8 模型能力必须包含输入与输出模态（原则已确认，字段待设计）

模型能力登记不能只记录“是否支持推理”或“是否支持工具”，至少要分别描述输入和输出能力。第一版能力分类可覆盖：

- 输入：文本、图像、音频、视频，以及经适配器解析后的文档或文件内容；
- 输出：文本、结构化数据，以及图像、音频、视频等生成类型；
- 相关非模态能力：工具调用、结构化输出约束、上下文长度、流式传输和原生思考强度参数。

“文件”是容器，不等同于模型原生支持某种模态。例如模型可能不支持原生 PDF 输入，但系统可以先解析 PDF 文本后再发送。每项能力应标明支持层级：原生支持、经 Nautilus 适配处理、明确不支持或尚未验证。任务是否可执行，应由任务所需能力、Provider 状态和模型登记共同判断，不能仅凭模型名称或 Prompt 猜测。

## 10. Agent 角色边界

### 10.1 用户看到的入口

用户不应被迫理解多个内部 Agent。产品表面上是一个连续的 Nautilus，主要有两个交互场景：

1. **学习教练**：日常默认入口，跨计划协调、恢复节奏和推荐下一步。
2. **任务学习环境**：进入具体任务后，深度教学、答疑、练习和工具执行。

计划分析和 Research Agent 通常在后台运行，只在需要用户确认路线、来源冲突或高影响变更时呈现结果。

与当前代码的范围映射方向为：

```text
global      -> 学习教练的跨计划协调上下文
plan        -> 计划分析、成果图谱和排期上下文
task        -> 当前任务的教学、执行和证据上下文
independent -> 临时讨论，默认不写入长期学习状态
```

这些是同一 Runtime 的不同范围和 Profile 组合，不是四套互不相干的 AI 产品。

一次完整的 Agent 执行环境由以下部分共同构成：

```text
统一 Agent Runtime
  + 当前角色契约
  + 当前数据范围
  + 显式工具授权
  + 沙箱与资源限制
  + 预算、超时、审批和审计
  = 本次完整 Agent 执行环境
```

学习教练、计划 Agent、任务 Agent 和 Research Agent 没有各自独立的“运行模式”。它们的差异来自本次被装配的职责、可见数据和工具权限；Runtime 的执行、隔离、审批和审计机制保持统一。

### 10.2 角色职责

| 角色 | 主要职责 | 不能做的事 |
| --- | --- | --- |
| 学习教练 | 今天做什么、为什么做、如何恢复、提醒和跨计划连续性 | 不应凭人格临时修改正式计划或静默创建大量任务 |
| 计划 Agent | 分析路线、成果图谱、负载、顺序和排期，提出变更草案 | 不应绕过确认直接写入高影响计划变化 |
| 任务 Agent | 当前任务教学、答疑、练习、实验、产出和证据收集 | 不应直接修改长期计划或把观察写成事实 |
| Research Agent | 搜索来源、核对领域关系、生成临时成果图谱 | 不应直接改正式图谱或正式计划 |
| 调度器 | 根据时间、状态、依赖和优先级筛选可执行任务 | 不是 Agent，不负责自然语言教学或价值判断 |
| Nautilus Core | 领域事实、状态转换、权限、审批、审计和回放 | 不负责替代领域知识来源判断真理 |

### 10.3 任务下发责任链

```text
Core/调度器筛选当前可行任务
  -> 计划 Agent 分析路线和取舍
    -> 学习教练解释并向用户推荐
      -> 用户选择或确认
        -> 任务 Agent 接管具体执行
```

任务 Agent 在会话内可以临时拆分步骤，但默认不把步骤直接写入正式计划；跨会话追踪才提出正式任务变更草案。

任务 Agent 如果发现问题超出当前任务范围，可以提交“升级请求”，说明为什么需要计划级或全局级信息、最小所需数据和希望完成的分析。Runtime 可以将工作委托给计划 Agent 或学习教练，但任务 Agent 本身不能通过修改 Prompt 或递归派生直接获得更高范围权限。

### 10.4 全局 Agent 的默认最小权限

全局学习教练拥有跨计划的导航和协调责任，但默认不能：

- 读取每个任务的全部私密产出原文；
- 读取没有被当前工作明确授权的任务级对话或附件；
- 直接运行任务级工具、代码沙箱或实验环境；
- 直接替用户确认任务成果或修改任务内部学习证据。

全局 Agent 默认读取 Core 提供的最小必要摘要、状态和证据引用。若它判断需要更细的任务信息，应通过受限访问请求取得经过脱敏、范围限定和审计的结果；需要执行任务工具时，应派生或委托给任务级 Agent，并通过交接包返回结果。

这不是为了制造角色隔离感，而是遵循最小权限、隐私保护、上下文控制和责任可追溯原则。用户可以明确扩大某次访问范围，但扩大范围本身也应成为可审计的决定。

### 10.5 子 Agent 权限

子 Agent 可以由父角色派生，但默认遵守委派契约：

- 数据范围更窄；
- 持久化写入权不高于父角色，通常更低；
- 工具权限按任务显式授予；
- 不能修改父 Agent 的状态、文件或未授权资源；
- 只返回事实、产出、观察、未知和变更草案；
- 派生深度、预算、超时和工具由 Runtime 控制。

权限必须通过 Runtime、工具接口、策略引擎、沙箱和领域命令强制执行，不能依靠系统提示词或人格 Prompt。

### 10.6 自动行为与确认边界

可以在权限范围内自动执行的低风险行为：

- 读取当前范围内的必要状态和引用；
- 计算进度、时间差异、冲突和候选优先级；
- 选择或切换当前会话的教学策略；
- 创建临时会话步骤、草稿和分析结果；
- 根据确定性规则安排短回访候选；
- 汇总事实、观察、未知和来源；
- 提醒用户已存在的任务、冲突和恢复入口。

必须经过用户确认或明确授权的高影响行为：

- 创建、删除、批量修改或重排正式计划和任务；
- 改变目标范围、完成标准或学习契约；
- 把临时成果图谱升级为正式领域关系；
- 保存长期人格、学习模式或个人策略修改；
- 扩大 Agent 的数据读取范围；
- 启用网络、代码执行或其他高风险工具；
- 把用户声明、AI 观察或临时假设升级为长期决定。

确认要求由 Core/Runtime 的结构化命令和审批策略执行，不能让 Agent 在自然语言中自行判断“用户大概同意了”。

### 10.7 全局 Agent 的主动权限申请（已确认）

全局 Agent 默认只读取跨计划的最小摘要、状态和证据引用。当现有上下文不足以完成当前分析时，必须通过 Core 主动向用户申请更具体的访问权限，不能自行扩大数据范围。

权限申请不是权限本身，必须是结构化、最小范围、有限时效且可撤销的请求，至少说明：

- 为什么需要这些信息，以及它将支持哪个具体判断；
- 涉及的计划、任务、委托、会话或资料范围；
- 需要的内容粒度：元数据、结构化摘要、必要摘录或原文；
- 授权时效：仅本次分析、当前会话或其他明确期限；
- 用户拒绝后的替代方案，例如由用户自行概述或提供指定片段。

默认用户动作应优先提供“允许这一次”“只提供摘要”“换一种方式”“拒绝”等窄选项。长期或宽范围授权不得在普通对话中隐式建立，应进入独立的权限设置流程。

Core/Runtime 必须同时执行以下约束：

- 有效权限取用户授权范围与 Agent 角色上限的交集；
- 读取授权不等于写入计划、证据、成果状态或委托的授权；
- 全局 Agent 不能把本次获得的内容自动转交给其他 Agent；
- 授权、拒绝、过期和撤销都写入审计记录；
- 用户拒绝后，Agent 必须说明可见范围限制并基于现有信息继续，不得猜测未授权内容。

高影响判断、权限缺失、隐私、费用或外部工具需求应在接近实际决策时申请；普通补充信息可以在会话边界批量申请，避免连续打扰。权限申请本身不扩大 Agent 的写入权限、角色权限或事实确认权。

### 10.8 首片权限与失败路径的用户体验验收（已确认）

P1-4 沿用第 10.4、10.7、17.14 节的权限和复核原则，以及第 64 条的 AI 失败规则，将它们落实到首片两个连续验收门，不新增权限模型：

- 事实闭环验证跨身份和同一用户内部全局/计划/学习行动范围的隔离，Core/Runtime 拒绝越权读取和未授权写入；AI 未启用时，会话和原始产出仍可保存并在重新打开后读取。
- 证据闭环验证全局 Agent 默认只读最小摘要、状态和引用，未经授权不读原始文本；摘要、引用和复核卡不得泄露未授权原文。
- 权限申请说明目的、范围、内容粒度、时效和拒绝后的替代方案；批准只开放限定读取，拒绝、过期和撤销后不得继续读取，所有结果可审计，读取授权不扩大写入权。
- 拒绝 Agent 读取权限后，用户仍能在自己有权访问的学习行动中继续学习、保存会话和产出。Agent 基于已授权信息继续，说明判断限制，不猜测未授权内容；用户自行查看产出不等于授权 Agent 读取。
- 复核卡标明哪些依据受权限限制，保留暂不处理和安排验证的选择；在 Agent 参与的复核中，原文展开沿用用户和当前 Agent 均有权限的规则。
- AI 不可用、超时、取消或输出不合格时，界面分别表达产出保存结果和分析失败结果；重新打开后产出可读，用户可重试、请求人工复核或安排补充验证，不生成空主张或伪造状态。

这些要求须同时验证 Core/Runtime 边界和实际用户流程，尚未实现。具体字段、组件、文案和测试工具留待工程规格。

## 11. 学习交接协议

### 11.1 MCP-inspired，但不是 MCP

学习交接协议可以借鉴 MCP 的设计思想：

- 能力协商；
- 工具和资源显式声明；
- 资源引用而不是复制全部上下文；
- 请求 ID、进度、取消和错误模型；
- 协议版本和兼容策略；
- 客户端/服务边界。

但二者职责不同：

```text
MCP：能力如何接入和调用
Nautilus 学习交接：学习工作如何交接、证据如何返回、状态如何长期演进
```

Nautilus 不应把每个内部 Agent 都拆成 MCP Server。MCP 更适合作为外围能力插件接入协议，核心学习语义仍由 Nautilus 自己定义。

### 11.2 长期工作单而非一次性消息

学习交接不是：

```text
Request -> Response
```

而是：

```text
Learning Assignment
  -> Learning Session(s)
  -> Evidence Submission
  -> Core State Update
  -> Delayed Verification
  -> Coach Recommendation
```

原因是学习会话可能跨天、暂停、恢复、部分完成、等待延迟验证或因前置缺口改变路线。

### 11.3 交接包内容

交接包是角色切换时生成的、带版本的上下文快照，至少包含：

```text
任务身份和版本
学习委托身份和版本
为什么现在做这个任务
本次预期学习成果
已有证据引用
仍然未知的问题
用户当前时间、精力和日程约束
当前人格和学习模式引用
本次允许的工具和数据范围
任务完成标准/契约版本
停止条件和结果回传要求
父会话、来源 Agent、目标 Agent
handoff_id 和协议版本
```

交接包优先传递 `task_ref`、`outcome_refs`、`evidence_refs`、`artifact_refs` 和 `conversation_refs`，不复制整个计划或全部私密聊天；Runtime 按权限解析引用。

### 11.4 交接结果

任务 Agent 返回结构化结果：

```text
事实：实际用时、执行步骤、工具调用、产出
观察：能独立完成什么、哪里稳定或不稳定
未知：哪些维度仍未验证
反面证据：错误、失败、误解或不一致回答
阻塞：学习、资料、工具或环境问题
偏好信号：任务粒度、节奏、学习模式反馈
变更建议：拆分、延期、补强、复习或调整路线
```

结果必须回到 Core。Agent 不直接调用另一个 Agent 修改状态。

### 11.5 版本与过期保护

交接包、学习契约和任务都必须带版本。任务被用户修改后，旧 Agent 的迟到结果不能覆盖新版本；Core 应拒绝过期写入或将其标为待审查。

### 11.6 上下文最小化与去重

为避免不同层级 Agent 重复回答、重复携带同一上下文和不断膨胀对话：

- Agent 优先读取 Core 的结构化状态、事件摘要和资源引用，不反复复制完整历史；
- 交接包记录已经确认的事实、已回答问题、未知和当前契约，目标 Agent 不应重新询问已有可靠答案；
- 全局、计划和任务会话分离保存，但通过任务、委托、证据和 `handoff_id` 关联；
- 上下文快照记录来源版本和截断信息，避免旧摘要被当作最新事实；
- 相同事件或证据使用稳定 ID 幂等提交，避免多个 Agent 重复写入；
- 用户主动切换层级时，界面应说明当前关注范围，不要求用户重新复述已经持久化的信息。

## 12. 主动运行与日常学习闭环

### 12.1 受限主动运行

主动运行由确定性事件触发，Agent 负责分析和提案。典型触发点：

- 任务完成；
- 证据提交；
- 关键任务延期；
- 复习到期；
- 时间估算持续失真；
- 计划冲突；
- 日复盘或周复盘。

高影响的计划、路线、时间和任务变化必须经过用户确认。Agent 不能因为“主动”而拥有额外写入权。

### 12.2 日常闭环

目标闭环为：

```text
学习教练预检状态
  -> 用户输入今天可用时间和精力
  -> 调度器筛选下一行动
  -> 选择合适学习模式
  -> 任务 Agent 执行
  -> 记录产出和证据
  -> 执行状态与学习状态分别更新
  -> 计划 Agent 后台分析
  -> 用户确认高影响调整
  -> 日终沉淀事实、观察和模式信号
```

当前代码已经具备计划、任务、计时、完成/撤销、对话和分级 AI 入口；真实学习证据、主动协同、状态账本、复盘和自适应调度仍未成立。不能把页面能力拼接宣传成已经完成的长期闭环。

## 13. 时间模型与校准

### 13.1 不采用固定“12 周计划”

固定写出 12 周或其他长期精确周期会制造虚假确定性。Nautilus 必须区分：

```text
有效学习时间：真正投入的分钟数
学习区块时间：一次连续学习可承受的时长
日历跨度：受到日期、间隔和生活安排影响的时间
```

不能用一个固定比例代表每个人所有任务的学习速度。

### 13.2 自适应承诺窗口

计划视野随状态可信度增长：

- 初次使用：只承诺接下来 1-3 次学习会话；
- 获得若干真实信号后：扩展到 3-7 次会话；
- 节奏稳定后：才展示一到两周的具体安排；
- 更远内容只保留低精度阶段和成果节点。

日历天数不是固定校准周期，用户投入的学习会话和获得的信号才是主要单位。高频用户可能一两天取得信号，低频用户可能跨两周但只投入少量时间。

### 13.3 校准信号

校准不以“过了 7-14 天”为完成条件，而看是否获得了足够信号，例如：

- 完成过不同类型的代表性任务；
- 有多次相对独立的学习会话；
- 记录了预计时长与实际时长差异；
- 至少有一次回忆、变式或迁移验证；
- 用户对任务粒度、学习模式和节奏产生了实际反馈。

这不是硬性固定数量，而是一个由 Core 根据不确定性和风险判断的信号门槛。

### 13.4 估计输出

系统应输出范围、假设和置信度，而不是虚假精确时长。短期安排具体、远期安排模糊；时间效率、学习效果和用户偏好必须分开建模。

## 14. 首次输入目标的初始化流程

### 14.1 已确认的总体流程

```text
用户输入目标
  -> 目标歧义解释
  -> 目标结果和完成标准
  -> 来源与知识包检查
  -> 正式路线或探索模式分流
  -> 临时/正式学习成果图谱
  -> 高影响约束确认
  -> 低成本首轮校准
  -> 自适应承诺窗口
```

### 14.2 目标解释卡

用户输入“学习大模型推理全流程”时，Nautilus 不应直接给出精确的长期计划，而应先生成解释卡：

- 可能的目标结果；
- 目标范围与排除范围；
- 目标层级：了解、会使用、独立实现或优化；
- 可能的完成证据；
- 当前仍不确定的词语和范围。

用户主要确认“这是不是我真正想要的目标，以及愿意接受什么取舍”，而不是被迫验证陌生领域的完整知识结构。

#### 14.2.1 自然表达约束（已确认）

上面的字段和示例只描述解释卡需要承载的信息，不是面向用户的固定问卷或逐字提示。系统必须保留用户最初的原始表达，再根据当前上下文生成少量、自然、简洁且容易回应的结果描述；真实文案应像理解了用户之后的正常对话，不能机械罗列“请选择目标层级”“请确认意图清晰度”等内部问题，也不能把数据库枚举直接暴露给用户。

默认卡片只呈现用户当前需要比较的结果差异，例如“最后能做什么”、一个代表性产出和关键取舍；来源、排除范围、证据要求及系统判断放入可展开详情。文案可以由模板填充或由模型润色，但必须受结构化字段、来源和权限约束，文案变化不能偷偷改变目标范围、完成标准或证据归属。

### 14.3 必须确认、可默认和必须测量

必须先确认的高影响信息：

- 目标边界；
- 期望能力层级；
- 什么结果算完成；
- 硬截止日期；
- 不可接受的内容或取舍；
- 会显著改变路线的个人限制。

可以先用低置信度默认值：

- 任务粒度；
- 第一版路线顺序；
- 初始复习间隔；
- 推荐学习模式；
- 初始时长估计；
- 首批资料排序。

必须通过行为测量：

- 真实学习速度；
- 是否能独立完成；
- 记忆保持情况；
- 合适的学习区块长度；
- 容易拖延的任务类型；
- 哪种学习模式实际有效。

### 14.4 探索模式

当领域来源不足、目标含义不明或用户无法判断路线时，进入探索模式：

- 标记临时性和来源缺口；
- 关键关系不能成为硬前置；
- 先安排低成本、可撤销、能够推翻假设的探测任务；
- 不把路线包装成权威计划；
- 在取得来源和行为信号后再升级为正式计划。

### 14.5 陌生领域中的目标澄清

当用户不熟悉领域时，不能要求用户先判断 AI 的领域路线是否正确，也不能要求用户回答自己无法理解的专业选项。目标初始化必须把两类判断分开：

- 用户判断“哪个结果更像我真正想要的”；
- 来源、实践验证和探测任务共同判断“领域关系和验证方式是否可靠”。

系统不直接询问抽象的“理论/实践/优化”选择，而是展示若干**结果示例卡**。每张卡用用户可理解的结果描述说明：最终能做什么、会产生什么可检查的成果、不包含什么、需要什么证据，以及选择它的取舍。用户选择的是期望结果，不是领域知识结构的正确性。

目标澄清必须允许以下正式选项：

- 更接近某个结果；
- 想组合多个结果；
- 我不知道；
- 都不是。

“我不知道”不是失败，也不应触发无限追问。它会使目标保持为**可逆目标假设**，并转入探索模式。系统通过有限轮澄清和低成本探测任务，让用户亲身体验不同类型的活动，再询问哪种结果和活动更接近真实目的。

目标状态的推荐演进为：

```text
目标假设
  -> 用户意图部分确认
  -> 来源检查
  -> 探索中
  -> 目标边界逐步稳定
  -> 正式目标
```

只有当未知会改变路线、完成标准、前置关系、时间投入或证据类型时，才必须优先探测；资料排序、任务命名等低影响未知可以先使用默认值。探测任务必须低成本、可撤销，并且能够推翻系统最初的目标假设，而不是只为证明 AI 最初的路线正确。

Core/Runtime 必须限制目标澄清循环：经过有限轮仍无法收敛时，自动进入探索模式，由系统降低问题难度并承担更多探测责任，不能把定义责任无限推回用户。

### 14.6 渐进披露与方向探测会话

目标初始化不能把系统内部完整的来源检查、目标假设、证据缺口、风险分析和路线推断一次性展示给用户。它们必须被结构化保存并允许按需展开审查，但默认界面在每一步只暴露用户**现在必须决定的一件事**。

结果示例卡默认只表达用户能够理解的结果差异，例如“最终能做什么”和一个代表性产出；来源、排除范围、证据要求和系统置信度进入二级详情。不能为了证明 AI 思考充分而把内部分析变成一大段入门问卷或聊天回复。

用户选择“我不知道”时，系统进入**方向探测会话**，而不是继续追问抽象专业术语，也不是进行一场隐藏考试。方向探测由少量、低成本且彼此有区分度的代表性活动组成，让用户实际接触不同类型的学习结果。例如针对“大模型推理过程”，可以分别观察一次输入到输出过程、运行或观察一个最小推理示例、解释一个延迟/显存/部署现象。

方向探测同时校准三个维度：

```text
意图清晰度：用户真正想获得哪类结果
领域可靠度：当前路线和完成标准有多少来源支持
执行可行性：用户现有基础、环境和学习方式能否支持下一步
```

探测过程中不生成伪精确的完整长期计划；系统只维护可逆目标假设、当前未知和下一项最小行动。用户每次只需回答低专业度、基于亲身体验的问题，例如“哪一种活动更接近你真正想做的事”，不需要审核陌生领域知识图谱。

### 14.7 熟悉领域用户的自主持径与动态分流（已确认）

探索模式不能成为所有用户的必经流程。用户已经明确目标、范围和路线时，应允许直接进入计划建立或任务执行；系统只做后台一致性检查和可选的风险提示，不得为了“验证 AI 的路线”强迫用户重复选择结果卡或完成探测。

系统内部根据用户当前信息准备程度区分三种状态：

```text
路线已知：用户已经有学习安排、教材、章节、任务清单或现成计划。
目标已知、路线未知：用户知道想学什么，但还没有具体安排。
目标仍需探索：用户还没有完全想清楚希望得到什么结果。
```

它们可以对应面向用户的自然表达：“我已经有学习安排”“我知道想学什么”“我还没完全想清楚”。但这三项不是必须阻挡在入口处的固定问卷。Nautilus 应先理解用户已经说出的内容，据此推荐最合适的下一步；只有信息不足或判断会显著影响后续路线时，才展示必要选项让用户决定。

动态分流必须持续响应用户后续反应，而不是首次选择后永久锁定。用户可以在任何阶段改道，例如执行既有计划时请求检查，规划过程中直接提供自己的路线，或在学习后发现方向不合适而进入探索。

系统可以根据结构化信号实时推荐路径和下一行动，但不得只依赖模型自由发挥。Runtime/Core 至少应保存：用户明确表达的目标和路线、信息来源、当前未决问题、系统推荐及其理由、用户最终选择。系统推荐不能自动修改正式计划、范围或完成标准。

“检查计划”不作为独立的一级状态，因为无论路线来自用户还是 AI 都可能需要检查；它应当是每条路径中的可选动作。直接执行路径中的第一次会话仍可用于校准真实学习速度、环境可行性和任务粒度，但它校准的是**执行参数**，不是质疑用户已经表达清楚的目标。

用户提供的路线、资料和任务应保留“用户提供”来源标记。AI 可以指出矛盾、缺口和风险并提出修改草案，但不能静默重写用户方案；涉及正式计划、完成标准或范围变化的修改必须由用户确认。

### 14.8 用户界面语言边界

“可逆目标假设”“意图清晰度”“领域可靠度”“证据缺口”等是 Core/Runtime 的内部字段，不作为默认用户文案。用户界面应使用面向行动的自然语言，例如“先试一步”“按我的方案开始”“帮我检查关键风险”“调整方向”。详细来源、判断依据和状态解释可以通过“查看依据”或类似的按需入口展开。

### 14.9 可变化的学习起点（已确认）

学习起点是用户当前愿意尝试的出发位置，不是一次性创建后不可修改的正式目标。用户在第一次行动前或行动后发现起点不合适时，都可以选择新的起点。

改变起点时必须区分“改变当前方向”和“删除过去记录”：

```text
当前起点：接下来从哪里继续
历史尝试：之前看过什么、做过什么、产生了哪些反馈和证据
```

改变当前起点不能静默删除历史尝试、学习产出或证据。系统应保存起点版本、变更时间、变更原因（若用户愿意提供）以及与之前起点的关系。旧起点可以标记为“暂不继续”，但仍可恢复、查看或重新采用。

起点变化至少支持三种用户意图：

- **换个入口**：保留当前方向，只换一种更合适的第一步，例如从先读理论改为先运行示例；
- **缩小或扩大范围**：仍学习同一主题，但调整到更窄或更宽的结果；
- **换个方向**：当前学习方向不再符合用户预期，保留原尝试后转向新的结果。

用户界面不必展示“起点版本”之类的内部术语。默认动作可以叫“换个起点”“调整方向”或“从别处开始”，并明确告诉用户已有记录会保留。系统不应因为用户改变起点就把之前的学习判定自动清零；过去证据是否仍支持新方向，需要由 Core 根据成果关系重新判断。

学习起点只有在用户明确继续、已有安排足够清晰，或系统获得了足够的范围和执行信号后，才逐步升级为正式计划。升级前的所有安排都必须保持可撤销、可编辑和低承诺。

### 14.10 学习路径可视化（方向已确认，细节待设计）

用户确认学习路径应当提供可视化表达，尤其要直观呈现学习起点的变化、当前主线、已经尝试的分支、暂时放下的方向和可以重新进入的位置。

第一原则不是“把所有对象画成图”，而是帮助用户回答：

```text
我现在从哪里继续？
我为什么走到这里？
之前尝试过哪些方向？
哪个分支可以恢复？
接下来有哪些可选路线？
```

为了避免图形失控，推荐只把有长期意义的学习阶段、成果节点、起点变化和路线分叉作为主节点；单次消息、细碎操作和普通任务默认收纳在节点内部，不全部暴露为图节点。否则长期使用后会形成无法阅读的“意大利面图”。

路径图至少需要区分：

- 当前主线；
- 已完成或已有支持证据的路径；
- 尝试后暂停的分支；
- 尚未选择的候选方向；
- 当前所在位置；
- 用户可以恢复或设为当前主线的历史节点。

改变学习起点时，默认创建新的路线分支或主线版本，而不是覆盖旧路线。用户可以查看当时为什么调整、产生了什么学习记录，并从旧节点重新继续。AI 可以推荐切换路线，但不能未经用户确认改变当前主线。

该能力目前尚未在代码中实现。视觉布局、节点密度、缩放方式、移动端形态和最终视觉风格仍需单独设计，但不得改变上述语义分工。

### 14.11 计划执行结构（已确认）

当前“科目 -> 主题 -> 任务”存在语义混用：科目是学校或领域分类，主题是知识目录，任务是行动对象。它适合课程型和考试型学习，但对项目学习、能力培养、转行和多路径探索不够自然。

候选方案：

1. **只改名称**：`计划 -> 模块 -> 子主题 -> 任务`。改动小，但仍然把知识分类和行动混在固定层级中，不能解决根本问题。
2. **成果导向树**：`计划 -> 学习方向 -> 学习成果 -> 学习行动`。语义最贴近“最终能做什么”，但一个成果可能由多个方向和行动共同支持，硬塞进单棵树会产生重复节点和分叉冲突。
3. **灵活执行树 + 独立成果图（已确认）**：`计划 -> 学习模块（可嵌套） -> 学习行动`；“学习成果”作为独立对象，与模块和行动建立可追溯关联；学习路径图负责展示主线、分支和起点变化。

推荐方案的语义边界：

```text
学习目标：为什么学、最终想得到什么结果
学习计划：当前采用的路线与安排
学习模块：当前计划中的一个可组织单元，可以是领域、章节、项目阶段或实践方向
学习行动：一次可以执行、计时、产出和复盘的具体行动
学习成果：用户最终要能够理解、解释、实现或迁移的能力对象，不强制成为执行树节点
```

“阶段”不作为固定层级，而作为模块或行动的时间/路线属性。这样可以避免把“基础、强化、冲刺”或“理解、实现、优化”硬编码成每个计划都必须存在的层级，也更适合用户改变学习起点和切换路线。

对用户而言，默认可以使用更自然的“计划 / 学习模块 / 学习行动”三个词；模块可嵌套，但不要求用户理解数据库中的固定层级。此前关于先做 `subject/topic/task` 兼容映射的建议，已被后续“允许破坏性领域重构”的决定取代。

### 14.12 学习模块的最小语义与破坏性领域重构（已确认）

“学习行动”暂不作为新的独立实体名称。为避免与已有的学习委托、学习会话混淆，建议保留用户可理解的“任务”称呼，并把任务定义为计划中的**可执行学习行动**：

```text
模块：组织一组相关任务
任务：一次可执行、可计时、可产出和可复盘的计划节点
学习委托：围绕任务展开的一段长期协作工作单
学习会话：真实发生的一次学习过程
学习成果：最终要具备的能力对象
```

学习模块的最小字段建议只有：标题、可选父模块、排序位置、可选说明、来源标记和生命周期状态。模块不直接保存完成度、学习时长、掌握度或证据结论；这些内容从任务、会话和成果证据派生。

由于当前版本的层级语义和用户体验已经被确认不满意，后续实现不需要把旧 `subject/topic/task` 作为产品或 API 兼容约束。可以直接建立新的规范领域模型、重写相关前端和接口，并删除旧的固定层级语义。

这项破坏性重构只针对产品模型、代码接口和内部数据库结构，不授权未经确认删除用户已有的学习内容。若需要改变默认数据库，仍必须先做一致性备份、隔离演练、迁移校验和可恢复方案；现有迁移 `001`-`010` 不原地修改，未来从新迁移或新的明确基线开始。

模块是**可选容器**而非强制层级：计划可以直接拥有任务，也可以在复杂度出现时创建和嵌套模块。这样探索阶段不必为了记录一项任务先创建空的“科目”或“主题”，也更符合学习起点低承诺、可变化的原则。

## 17. 终局产品路线（综合整理版）

本节不是 MVP 分期，也不是已经批准的工程排期，而是把此前讨论提炼成一条**终局产品的因果和依赖路线**。它回答“用户如何长期使用 Nautilus”和“系统概念应先依赖什么”，未来实现时可以重新安排具体先后，但不能打乱这些语义关系。

### 17.1 终局主链

Nautilus 的长期协作主链应保持为：

```text
学习意图
  -> 学习成果
  -> 当前起点与学习路径
  -> 计划与学习模块
  -> 任务
  -> 学习委托
  -> 学习会话
  -> 产出与学习证据
  -> 可信学习状态
  -> 复盘、调整与下一行动
  -> 新路径或新一轮委托
```

其中：

- **学习意图**回答“我为什么想学、想变成什么样”；
- **学习成果**回答“最终能够理解、解释、实现或迁移什么”；
- **学习路径**回答“从哪里开始、有哪些可能路线、当前选择哪一条”；
- **计划和模块**回答“当前采用什么组织方式和学习承诺”；
- **任务**回答“现在要做哪个具体行动”；
- **委托**回答“这一轮协作要验证什么、边界是什么、何时算这份工作结束”；
- **会话、产出和证据**回答“实际上发生了什么”；
- **可信状态**回答“哪些已经有证据支持、哪些仍未知或需要回访”；
- **复盘和调整**回答“下一步是否继续、补强、换起点或切换路线”。

这条链把“想学什么”“要做什么”“做过什么”和“是否真的形成能力”分开，但又通过关系和事件保持连续。

### 17.2 用户体验路线

从用户角度，终局 Nautilus 应该经历以下连续循环：

1. **表达想达到的结果**：用户可以直接说目标，不必先填写完整课程表或判断陌生领域的专业路线。
2. **理解当前意图**：系统通过结果示例、来源说明和少量探测，判断这是已有路线、目标明确但路线未知，还是仍需探索；用户始终可以改道。
3. **形成可变化的起点**：系统提出低承诺的起点和可逆假设，用户可以接受、调整、换入口或保留多个候选分支。
4. **形成学习成果与路径**：把“要能够做什么”和“准备怎么走”分开表达；路径可以有主线、暂停分支、历史版本和可恢复位置。
5. **建立计划与任务**：用户确认当前计划、可选模块和任务组织方式；不强制使用固定的科目/主题层级。
6. **创建学习委托**：围绕一个任务形成学习契约、证据要求、时间预算、学习模式、工具权限和停止条件；AI 提议，用户确认。
7. **进入学习会话**：任务 Agent 在受 Runtime 约束的环境中教学、提问、执行练习、运行工具和收集产出；模型策略由用户选择，学习模式和人格可以独立变化。
8. **形成证据并进行延迟验证**：系统记录解释、代码、实验、练习、迁移和跨时间回忆，区分即时证据、延迟证据、用户声明和反面证据。
9. **更新可信状态**：Core 根据事实和证据更新执行状态、学习状态、成果支持程度、未知项和回访候选；AI 只能提交观察、推断和建议。
10. **复盘并调整下一步**：学习教练解释“已经确认什么、仍然不知道什么、这会不会影响下一步”，用户决定继续、补强、改时间、换起点或切换路径。
11. **长期协同多个计划**：当用户有多个目标时，全局学习教练负责导航、优先级解释和冲突提示；计划和任务 Agent 负责各自范围内的深入工作，委托可以并行开放，但具体操作仍受单会话和权限约束。

这不是一次性向导。任何阶段都允许回到前面的步骤，但回退应创建新版本、分支或决定记录，不覆盖历史事实。

### 17.3 终局系统依赖路线

从系统设计角度，概念依赖关系建议按以下顺序建立：

1. **Nautilus Core 与事件账本**：先定义事实、观察、推断、决定、用户确认、撤销和审计，确保模型不会直接成为事实写入者。
2. **学习成果与证据模型**：定义能力节点、证据来源、证据可信等级、反面证据、延迟验证和状态派生；这是“做过”和“学会”分离的基础。
3. **起点、路径与执行结构**：定义路径版本、主线/分支、计划、可选模块、任务及其关系，让路线可以变化而不丢失历史。
4. **学习委托、契约与会话**：定义长期工作单、版本化完成标准、交接包、多次会话、停止条件和并行委托模型。
5. **统一 Agent Runtime**：把角色契约、上下文范围、工具权限、审批、委托、超时、预算和子 Agent 派生放进运行时强制执行。
6. **人格 Profile 与学习模式**：在 Runtime 之上分别定义表达风格和教学协议；苏格拉底、费曼、练习优先等模式不是一句 Prompt，而是可执行的交互状态机。
7. **模型策略与能力登记**：实现全局/计划/任务/对话逐级覆盖，登记输入/输出模态和适配状态；模型策略由用户选择，Nautilus 只建议升级，单次运行冻结配置。
8. **学习教练与主动复盘**：在可信状态和 Runtime 已存在的前提下，提供今日重点、恢复入口、候选委托、冲突提示、回访和长期节奏分析。
9. **资料、知识包与能力插件**：接入文档解析、代码沙箱、搜索、题目验证、日历等受控能力；知识包声明领域关系，插件负责执行验证。
10. **可视化与生态**：呈现成果图、路径图、证据覆盖、交接和历史分支，并在权限和审查机制成熟后支持人格、学习模式和能力包共享。

这里的顺序是语义依赖，不代表必须按十个阶段线性开发。例如模型策略可以早于完整学习教练出现，但它不能绕过 Core/Runtime；路径图可以先做可视化原型，但不能在没有路径版本语义时把普通消息直接画成节点。

### 17.4 必须贯穿全程的不变量

- AI 可以提出、解释、观察和推断，但不能把自然语言或模型置信度直接写成事实。
- 计划、模块、任务和委托由用户管理；会话、计时、事件、证据、进度和掌握状态由 Core/Runtime 根据实际行为派生。
- 用户拥有目标取舍、路线切换、委托生命周期、模型策略和高影响变更的最终决定权。
- 模型能力、思考强度、人格、学习模式和工具权限分开管理；更强模型不能扩大权限。
- 所有路径变化、契约版本、证据和用户选择都可追溯、可撤销，历史不因改道而被删除。
- 系统优先说明未知和证据缺口，不为了显得完整而给出虚假的时间精度、掌握结论或领域权威性。

### 17.5 不应再作为主路线的方向

以下内容仍有价值，但不应成为终局设计的主轴：

- 先建立多个互相独立的 Agent，再尝试拼接学习状态；
- 先做完整百科知识图谱，再寻找个人学习用途；
- 先做模型市场、插件市场或高度开放的通用 Agent 平台；
- 先做漂亮的甘特图、复杂排期或大量提醒，再补可信状态；
- 用一个总分、单条遗忘曲线或一次答题替代证据组合和跨时间验证。

### 17.6 长期主索引采用双轴模型（已确认）

Nautilus 不采用单纯的计划中心或成果中心，而采用“用户工作轴 + 长期真相轴”的双轴模型：

```text
用户工作轴：计划 -> 学习模块 -> 任务 -> 学习委托 -> 学习会话
长期真相轴：学习成果 -> 证据覆盖 -> 学习状态 -> 延迟验证
连接层：学习意图、学习路径、任务支持关系、证据引用和版本决定
```

- 用户主要从计划和任务进入工作，管理当前承诺、组织结构、日程和执行动作；
- Core 以学习成果作为长期能力身份和证据归属，计划暂停、任务重排或路线切换都不应割裂已经形成的证据历史；
- 学习路径负责解释当前计划为什么支持这些成果、采用哪条路线，以及路线何时发生过变化；
- 同一个学习成果可以被多个计划、任务和委托支持；同一个任务也可以支持多个成果，但每条关系必须能够说明来源、适用范围和证据用途；
- 双轴不是两套互相复制的数据。执行事实保留在工作轴，能力状态保留在真相轴，通过稳定引用和事件关联起来。

因此可以概括为：

> 用户管理计划和任务，Nautilus 长期追踪学习成果和证据，学习路径解释两者为何相连。

### 17.7 分层学习成果模型（已确认）

双轴模型中的学习成果采用三层结构：

```text
综合成果
  -> 可验证成果
    -> 版本化达成标准
```

- **综合成果**表达用户真正想达到的整体结果，可以组织多个可验证成果，并在需要时接受综合实践或迁移证据；
- **可验证成果**是值得长期追踪的稳定能力身份，必须能够被单独观察、会影响后续路线，并可能被多个任务或计划复用；
- **版本化达成标准**定义当前计划或学习委托要求达到的深度、质量、允许帮助和证据组合。同一能力可以在不同计划中采用不同标准，不需要复制成果身份。

学习成果不是知识点名称、课程章节或任务标题。任务描述“准备做什么”，成果描述“最终能够做什么”。

该问题不能只靠标题去重。例如：

```text
理解 KV Cache 的基本原理
能够解释 KV Cache 的显存与吞吐权衡
能够在推理引擎中实现并验证 KV Cache
```

三者相关，但可观察行为、证据要求和适用情境不同，不能因为都包含 `KV Cache` 就自动合并。反过来，“解释注意力缓存机制”和“解释 KV Cache 原理”也可能只是不同措辞下的同一成果。

采用“可观察能力声明”作为可验证成果的稳定身份。一个成果至少需要说明：

```text
对象：关于什么
行为：用户能够做什么
情境：在什么范围、版本或环境中完成
```

具体质量门槛、是否允许查资料、需要何种迁移验证等内容进入版本化达成标准，不全部写入成果身份。仅修改名称或表述时保留成果身份；达成深度改变时建立新标准版本；行为、对象或适用范围发生实质变化时，建立新的成果或成果版本关系。

成果之间至少需要表达等价、包含、重叠和前置关系。AI 可以提出关系候选，但不能静默合并、拆分成果或迁移证据。任何会改变证据归属和长期状态的操作都必须可审查，并保留原始成果、标准版本和证据引用。

综合成果不能仅因为所有子成果都有部分支持证据就自动宣布成立；当综合能力要求跨成果协同或迁移时，仍应保留整体实践或综合验证。

### 17.8 原始产出、证据主张与派生状态（已确认）

学习成果的状态必须通过可追溯证据派生，不能由 AI 的印象、语言流畅度、置信度或无引用判断直接产生。证据模型把实际发生的内容和对其意义的解释分开：

```text
原始产出（内容）+ 关联事实事件（发生上下文）
  -> 证据主张
    -> 目标成果 + 达成标准版本 + 支持维度
      -> 派生学习状态
```

- **原始产出**保存用户实际回答、代码、笔记、实验结果、作品或外部评审材料等内容，不因为后续解释变化而被改写；
- **事实事件**记录何时、由谁、通过哪个学习会话和动作产生该产出；计时开始、会话结束等没有产出的活动也可独立记录为事件；
- **证据主张**说明某项原始依据对哪个成果、哪个标准版本和哪个能力维度提供支持、反面信号或不足；
- **派生学习状态**由当前可采纳的证据主张重算，不保存一个无法解释的永久掌握分数。

同一份产出可以支持多个成果或多个维度，也可以同时产生支持与反面证据。例如代码通过测试可以支持“功能正确”，但用户无法解释关键设计时，也会暴露“设计解释”维度仍不足。工具结果只证明工具实际检查到的性质，不能自动外推为理解、独立完成或迁移能力。

基于产出的证据主张必须同时引用具体原始产出及其关联事实事件，首片文本产出的候选主张均须满足；其他证据仍须引用其实际依据的事实事件或可核验外部来源，不为单纯活动事件人为创建产出。AI 可以依据这些材料生成结构化证据主张，指出支持、反驳、未知和建议验证项；但 AI 的评价本身不是证据来源。没有可追溯依据的 AI 判断只能记录为推断、候选假设或未知，不能推动成果状态升级。

证据主张至少需要保留：来源引用、发生时间、产生方式、使用的资料/提示/工具、独立程度、验证方法、目标成果、标准版本、支持维度、方向（支持/反面/不足）和隐私范围。原始依据保持不变，证据主张可以被质疑、撤销采纳、补充或被新证据反驳，但不能反向篡改已发生的事实。

用户自报可以作为“用户声明”保存，但不能伪装成独立验证；确定性工具结果由 Core 记录为事实；外部成绩或评审必须保留来源和验证状态；AI 生成的练习答案分析必须同时保留题目、用户原回答、帮助条件和评判依据。

综合成果不能简单平均子成果状态。子成果证据可以形成覆盖情况，但涉及跨能力协作、综合实践或迁移的综合成果仍需要相应的整体证据。

### 17.9 达成标准定义证据配方（已确认）

不同证据不使用单一全局权重或固定等级排行榜。不能建立简单的“工具证据 > 用户产出 > AI 判断 > 用户声明”顺序，因为不同证据证明的是不同性质：测试通过可以强力证明功能结果，却不一定证明独立实现或概念理解；一次无提示解释可以证明即时理解，却不能证明跨时间保持。

由版本化达成标准声明每个能力维度接受哪些证据类型、最低组合和失效/回访条件。证据本身记录来源、直接性、独立程度、使用的帮助、验证方式、情境范围和时间性质；状态计算只判断“当前标准需要的覆盖是否成立”，不把这些属性压成一个看似精确的总分。

证据的证明范围必须受到原始条件约束：在允许查资料的条件下完成，只能支持相应条件下的能力；获得关键提示后完成，不能伪装成独立完成；即时回答不能替代延迟回忆；同情境重复练习不能自动等同于迁移能力。

证据冲突不做正负分数抵消，也不删除旧证据。系统应定位冲突发生在哪个维度和条件下，并派生“存在矛盾”或“需要补强”等状态，再提出能够区分原因的最低成本验证。

### 17.10 AI 证据主张的分层采纳（已确认）

证据主张不能全部要求用户确认，也不能全部自动进入长期状态。采用三条通道：

```text
Core 可确定的机械事实
  -> 自动生效

AI 基于原始产出、标准和明确引用生成的语义主张
  -> 自动留痕为候选观察
  -> 可用于初步支持、未知项和下一步建议

影响稳定成果状态、完成结论、前置关系或路线变化的主张
  -> 需要独立验证或人工复核
```

AI 语义主张必须引用原始产出、事实事件或可核验来源，并标明支持、反驳或未知的具体维度。没有引用的“看起来已经掌握”等印象不能进入证据链。普通观察不要求用户逐条审批，但用户必须能够查看依据、提出异议、排除采纳或要求重新评审；用户认可一条记录不等于把薄弱证据变成客观事实。

稳定支持优先要求达成标准规定的确定性验证、跨时间/迁移证据或其他独立信号共同满足。分层采纳的目标是减少交互负担，同时把 AI 误判限制在可见、可撤销、不会直接宣布掌握的范围内。

### 17.11 证据主张双维度模型（已确认）

用户确认：**证据主张的审查生命周期与其对学习状态的贡献分离建模**。如果只使用一个 `accepted/rejected` 字段，会混淆以下不同情况：

- AI 主张引用完整，但只足以形成初步支持；
- 用户提出异议，主张暂时不能用于稳定状态，但原始产出仍然有效；
- 新的独立证据支持了同一结论，旧主张仍应保留但不必重复计算；
- 达成标准换了版本，旧主张没有“错误”，只是对当前标准不再适用。

采用以下两个层次，但只有审查生命周期作为证据主张的持久化审计状态；证据适用性和成果状态由 Core 根据当前标准与证据集合派生：

```text
证据主张审查状态：候选 / 已采纳 / 被质疑 / 已撤销 / 已替代
证据适用性：可参与 / 被排除 / 已过期 / 当前标准不适用
成果维度状态：未知 / 初步支持 / 支持 / 存在矛盾 / 待回访
```

审查状态描述这条主张目前是否被系统采纳、质疑或替代；它不能修改原始产出，也不能直接把成果标记为稳定掌握。被质疑或已替代的主张保留在历史中，默认不参与当前状态计算，但仍可用于解释过去的判断和审计变更。

证据适用性由 Core 根据达成标准、帮助条件、独立程度、验证方式、情境范围、时间条件和冲突处理派生；用户点击认可不能把薄弱证据直接升级为稳定支持。成果维度状态由当前可参与的证据集合整体计算，而不是由单条主张填写。时间衰减和标准版本变化主要改变证据适用性或成果状态，不应把原始证据标记成发生过错误。

该设计可以同时满足可追溯性、可撤销性和长期重算能力，但会增加状态模型的概念数量。具体的持久化字段、派生计算实现和复核界面仍需另行设计，但不得破坏本节已确认的生命周期与贡献分离原则。

### 17.12 证据主张状态转换与批量复核（已确认）

本轮确认证据主张的审查状态采用保守、可追溯的转换规则；审查动作只改变主张生命周期，不直接填写成果状态。

#### 审查状态转换

```text
候选 -> 已采纳：Core 可确定的机械事实、确定性工具验证通过，或完成独立验证/人工复核
候选/已采纳 -> 被质疑：用户提出异议，引用范围不符，或出现明确矛盾证据
被质疑 -> 已采纳：用户撤回质疑，或复核确认原主张仍成立
候选/已采纳/被质疑 -> 已撤销：来源、归属或主张本身被确认不成立
候选/已采纳/被质疑 -> 已替代：有新主张明确接替同一范围、标准和证据解释
```

- 自动采纳范围必须很窄，只适用于会话结束、测试结果、文件提交、时间戳等机械事实，或有明确、可重复验证器的结果。
- 带引用的 AI 语义主张默认仍是候选观察，可形成初步支持，但不能仅凭模型判断自动形成稳定支持。
- 会导致稳定成果状态变化、关闭委托、改变前置关系或路线的主张，必须有独立验证或人工复核。
- 撤销表示主张本身不成立；替代表示旧主张被新主张接替，不能把二者混为一谈。撤销和替代均不原地恢复，需要纠正时创建新主张并关联旧记录。

#### 用户质疑与标准版本

- 用户质疑后，主张立即移出当前状态计算；原始产出、过去的派生快照和审计记录均保留，不做回溯性删除。
- 质疑只针对证据主张，不直接改写原始事实。若用户认为原始事件本身有误，应进入独立的事实校正流程。
- 达成标准换版本时，旧主张保留原标准版本和审查历史。只有存在明确兼容映射时，才可对新标准继续适用；否则由 Core 派生为“仅适用于旧标准”或“当前标准不适用”。
- 标准版本变化本身不触发撤销或替代；当新标准影响即将开始的行动时，再安排补充验证或批量复核。

#### 批量复核

批量复核是用户做一次决定的界面和审计边界，不是把多个原始观察压缩成一条不可追溯的新证据。复核卡可以合并同一成果、同一标准版本、同一学习会话或工作阶段、相近支持维度且无冲突的主张；存在不同方向、不同隐私范围或不同高影响动作时必须拆分。

复核优先在以下时机生成：学习会话暂停或结束、用户重新打开计划或成果、未处理主张达到待复盘条件、标准版本变化、成果状态即将发生高影响变化，或用户主动要求复核。用户可以按建议处理低风险项、暂不处理、展开单条依据或只处理例外项；每条主张仍分别写入审计事件。

普通机械事实、低风险观察、去重和时间适用性重算默认只留审计，在会话总结或下次回访中汇总。涉及长期状态、委托关闭、路线/前置关系、证据冲突、权限、隐私或费用的事项，必须在接近实际决策时提示用户。

默认用户界面不直接显示内部枚举，而使用“已有依据”“初步支持，尚需验证”“当前依据不足”“这条依据暂不计入当前判断”“存在不同表现”“已由更新记录接替”“仅适用于旧标准”等表达；详细状态、依据和转换原因放在可展开的记录详情中。

以上规则属于终局产品规范，尚未进入业务代码、数据库迁移或默认数据库；未来实现必须保留原始产出不可篡改、状态可重算和批量动作可撤销的边界。

### 17.13 成果维度状态派生（已确认）

成果状态按版本化达成标准中的能力维度和最低证据组合派生，不使用掌握百分比、全局证据权重或模型置信度作为状态依据。Core 先过滤当前可参与的证据，再逐项判断维度覆盖和证据条件。

推荐的状态顺序为：

```text
没有相关可用依据 -> 未知
有部分依据但证据配方未完成 -> 初步支持
同一维度存在尚未解决的相反表现 -> 存在不同表现
即时要求已满足但延迟/迁移验证未完成 -> 待回访
所有必需维度和最低组合满足且无未解决矛盾 -> 支持
```

成果维度采用“主要状态 + 原因标签”而不是把所有情况压成互斥枚举。原因标签可以说明：缺少哪一类证据、是否在资料或提示帮助下完成、是否只在特定情境成立、是否需要独立验证、是否存在延迟回访或迁移缺口。

- “未知”表示还没有足够相关观察；“依据不足”表示已有相关产出但尚未满足最低组合。
- 候选 AI 观察最多形成初步支持，不能单独满足稳定支持；机械事实和确定性工具结果只证明其实际检查的性质。
- 帮助条件、独立程度、情境范围和时间要求必须按标准原样约束证据证明范围，不能向更强能力外推。
- 矛盾证据不做正负抵消。功能正确、概念解释、独立完成、迁移和延迟回忆等维度可以分别得出不同状态，并在成果层面汇总未满足的缺口。
- 证据过期或延迟验证到期时，不改写原始记录；Core 只重新派生为待回访、依据不足或其他适用状态。

用户界面默认使用“还没有足够记录判断”“已有一些依据，但还缺少一次独立验证”“在有资料帮助下表现良好，独立完成尚未确认”“存在不同表现”“需要再次回访”等自然语言；详细覆盖维度、依据和计算原因按需展开。

该规则属于终局产品规范，尚未进入业务代码、数据库迁移或默认数据库。人工复核界面的具体布局、批量动作和撤销入口仍需单独设计。

### 17.14 人工复核界面（已确认）

人工复核不做成逐条审批收件箱，而采用“上下文触发的复核卡 + 全局待处理入口”。用户在学习会话结束、重新打开计划或成果，或即将发生高影响状态变化时，看到当前真正需要决定的事项；普通低风险观察不应持续打断学习。

复核卡先表达当前影响和建议，再允许查看具体依据。默认展示目标成果、当前标准、被合并观察的范围、代表性依据、缺口、帮助条件、验证方式和可见权限；原始内容只有在用户和当前 Agent 均有权限时才可展开。全局 Agent 无权查看的内容必须明确显示权限限制，不能通过摘要泄露原文。

用户动作使用自然语言，不直接暴露内部枚举：

- 按建议处理；
- 逐条查看；
- 这条判断不准确；
- 暂不处理；
- 安排一次验证；
- 撤销刚才的处理。

“按建议处理”仅适用于同一成果、同一标准、相近情境和风险等级、且不存在冲突的低风险主张。批量动作实际仍为每条主张写入独立审计事件，并重新派生成果状态。支持与反面证据、不同帮助条件、不同隐私范围、不同处理建议或会影响路线/委托的事项必须拆分。

“暂不处理”表示用户暂时不做决定，不等于认可或拒绝。系统记录该选择，在条件没有变化时不重复打扰；出现新证据、即将影响下一行动、标准变化或用户主动查看时再提示。

以下事项必须进入复核卡或明确提示：成果状态可能改变、矛盾证据、委托或契约变化、路线/前置关系变化、标准版本变化、额外权限、私密资料、费用或外部工具。机械事实、低风险观察、去重和适用性重算可以只留审计或在会话总结中汇总。

该界面原则属于终局产品规范，尚未进入业务代码、数据库迁移或默认数据库；未来实现必须保持批量动作可撤销、单条主张可追溯和权限边界可见。证据对象的具体字段命名、表结构和渲染组件属于后续工程规格，不再作为独立的产品方向问题反复讨论；实现时不得突破本节已经确认的引用、隐私和权限边界。

### 17.15 目标与计划的语义分离及界面渐进披露（已确认）

目标和计划在领域模型中是两个不同对象，但不要求用户在首次进入时同时维护两层。目标是较稳定的学习意图和期望结果，计划是实现目标的当前路线、时间安排和组织方式；一个目标可以关联多个计划，计划的结束或切换不等于目标完成。

用户界面默认以计划和任务为日常工作入口。单计划场景可将目标以“学习方向”或“希望达到的结果”呈现；只有在多计划管理、路线切换、长期回顾或跨计划成果出现时，才显式展示目标中心和关联关系。没有稳定目标的计划可以先开始，之后再建立或调整关联。目标、综合成果和计划必须保持语义区分：目标表达意图，成果表达可验证能力，计划表达当前怎么走。

该规则属于终局产品规范，尚未进入业务代码、数据库迁移或默认数据库；目标解释卡的自然表达约束已在下一节确认，首次行动和学习起点原则沿用前文已确认的动态分流与可变化起点规则。

### 17.16 目标解释卡与自然表达（已确认）

目标解释卡的字段是系统内部用于保持语义完整、来源可追溯和决策可审计的结构，不是用户必须逐项填写的表单。用户界面应保留原始输入，以少量结果示例帮助用户比较，并且只在当前确有必要时提出一个自然、上下文相关的问题。示例提示仅作为信息结构，不得直接变成生硬、重复或脱离上下文的固定话术；默认用户文案应优先使用贴近用户目标的行动语言，复杂依据和内部状态按需展开。

该规则属于终局产品规范，尚未进入业务代码、数据库迁移或默认数据库；用户选中结果后的可逆起点、首次行动由用户选择、历史保留和正式计划升级条件已在前文确认，不再作为独立产品问题重复讨论。

### 17.17 未来实现顺序另行处理

未来真正开始工程实现时，仍需单独制定备份、迁移、验证和部署计划；当前不因为本节的终局路线而修改默认数据库、既有迁移或业务代码。附件、Web Search、复杂甘特图、思考强度参数、社区市场和完整知识库等能力是否进入具体版本，留待终局语义稳定后再排定。

### 17.18 首片成功指标与护栏（已确认）

首片采用测量契约：先定义测量对象、分母、观察窗口、排除条件、来源事件和隐私保留边界，真实使用形成基线后再设业务目标值。指标分为产品价值指标、硬性护栏和诊断指标。

- 产品价值指标：中断后正确恢复委托比例、复核到下一行动完成率、证据可追溯率；主动切换委托、暂不处理、权限不足和等待验证等情形单独统计，不混入用户价值失败。
- 硬性护栏：无依据主张率为零；AI 失败时会话和原始产出保存并可重新读取，指定 AI 故障场景的事实保存成功率为 100%；事件重建一致；权限违规和隐私泄露为零容忍。
- 诊断指标：用户质疑率、暂不处理率、无合格标准时的降级比例、分析失败重试率和人工复核请求率。它们用于发现问题，不能直接按越低越好优化。
- 任一硬性护栏未通过，都不能宣称首片成功；具体事件字段、窗口、报表和采样实现属于工程规格。

该决定只定义测量边界，不预设未经数据支持的业务目标值；实际使用中的零分母、窗口未满和无样本必须单列，不能显示为虚假的成功率。

### 17.19 需求性质与交付范围分开标记（已确认）

PRD 同时描述终局方向和首个纵切片，后续规格必须把两个维度分开：需求性质区分“跨阶段不变量”和“具体功能”；交付范围区分“事实门”“证据门”“后续”和“暂缓”。一条不变量可以同时属于首片验收，例如原始产出不可篡改、权限边界和 AI 失败时保存产出；终局功能出现在 PRD 正文不代表本轮必须实现。

“待工程规格分解”只表示进入领域、事件、API、迁移、测试或恢复设计前的准备状态，不替代交付范围。首片需求建立稳定编号，工程规格和测试引用编号而不是易变的章节位置；当前编号索引和范围以 PRD 第 11.6 节为准。

### 17.20 产出删除、撤回与彻底删除边界（已确认）

三种用户动作分别处理内容生命周期和证据生命周期：

- **普通删除**是正常可用、可恢复的软删除，把内容从当前工作区隐藏并移入受控回收范围；若它参与证据计算，立即退出当前状态并重算，恢复时由 Core 按当前标准重新判断。
- **撤回**只处理证据适用性，不删除原始内容；产出仍可查看，依赖它的主张退出当前状态，用户可以在内容未彻底删除且标准仍适用时明确恢复。
- **彻底删除**是不可逆的隐私操作，清除或不可逆脱敏原始内容和可恢复副本；依赖主张立即失效，缓存、索引和普通备份不得恢复，删除前显示影响并要求明确确认，只保留不含私人内容的最小审计元数据。

事实纠正仍通过追加版本表达，不允许原地改写。普通删除、撤回和彻底删除不是同一动作，具体事件名称、回收站实现和恢复界面留待工程规格。

## 18. 已确认结论清单

截至 2026-09-05，以下原则视为已确认：

1. Nautilus 的定位是长期学习协作者，核心责任是维护目标、真实状态和下一行动的一致性。
2. AI 不能直接写事实、正式计划或长期学习状态；权限必须由 Runtime/Core 强制，不依赖 Prompt。
3. 事实、观察、推断、决定必须分层保存。
4. 执行状态与学习状态必须分离。
5. 学习证据需要多种信号，跨时间验证不能被一次即时回答替代。
6. 使用轻量学习成果图谱和个人证据覆盖层，不做第一版百科图谱。
7. 领域知识包声明式、可审查、可版本化；能力插件负责执行验证工具。
8. 人格 Profile 与角色职责、权限和学习模式分离；督学和任务 Agent 可以共享人格。
9. 用户可编辑的人格必须保留原文、结构化编译、校验、确认、版本和回滚。
10. 学习模式是 Runtime 交互协议，不是单句 Prompt；苏格拉底模式采用提示阶梯。
11. 用户体验上是一个连续的 Nautilus，内部采用学习教练、计划 Agent、任务 Agent、Research Agent 和调度器的职责分离。
12. 子 Agent 的权限由 Runtime、工具和委派契约约束，不能修改父 Agent 状态或未授权资源。
13. 学习交接协议借鉴 MCP，但不等同于 MCP；MCP 负责能力接入，Nautilus 协议负责学习工作、证据和长期状态交接。
14. 学习交接采用长期工作单、可恢复会话和延迟证据，不是一次性请求/响应。
15. 任务、学习委托、学习会话、证据/观察是不同层级；交接包是角色切换时冻结的上下文快照。
16. 学习契约必须在执行前形成、版本化并带标准来源；执行中不能静默改变完成门槛。
17. 用户和 AI 都可以提出完成；Core 确认客观事实；用户可以关闭本次委托；学习成果不能由 AI 单独宣布掌握。
18. 用户不懂领域时，只确认自己的目标和取舍；陌生领域标准必须由来源、实践验证和探索任务支撑。
19. 首次目标创建使用目标解释卡、来源检查、探索/正式分流、低成本校准和自适应承诺窗口。
20. 不采用固定 12 周或固定 7-14 天作为所有用户的计划时长；以未来若干学习会话和实际信号逐步扩展计划视野。
21. 内置学习教练符合直觉；人格和学习模式使用声明式可共享数据包，执行能力才做插件。
22. 当前阶段不为了丰富功能而优先扩展附件、Web Search、复杂甘特图或通用 Agent 平台。
23. 陌生领域用户不需要先验证领域路线，只需表达期望结果；系统通过结果示例、来源标注、可逆目标假设和低成本探测逐步收敛目标。
24. 目标初始化采用渐进披露；默认界面每一步只要求用户完成一个当前必要决定，完整来源、假设、证据和风险保留为可展开的系统信息。
25. “我不知道”进入方向探测会话；探测通过少量代表性活动共同校准意图清晰度、领域可靠度和执行可行性，不把探索伪装成考试或完整计划。
26. 方向探测行动由用户自主选择；系统可以推荐并解释原因，但不能替用户启动探测或未经确认执行会改变数据、环境或计划的操作。
27. Core/Runtime 的内部状态术语不得直接成为默认用户界面文案；默认表达应面向用户当前要做的行动，详细依据按需展开。
28. 目标初始化使用动态分流而非固定问卷：系统根据用户已表达的信息推荐“使用已有安排、协助制定安排或探索方向”，并随用户反应实时调整；用户始终拥有最终选择和改道权。
29. 动态分流必须由结构化状态和 Runtime/Core 规则约束，不能只依赖 Prompt 或模型临场判断；“检查计划”是各路径的可选动作，不是独立的用户类型。
30. 学习起点是可变化的当前出发点；用户可以换入口、调整范围或更换方向。改变起点不删除历史尝试、产出和证据，而是创建新的当前版本或分支，并允许恢复旧起点。
31. 学习起点在用户明确继续或信息足够稳定前保持低承诺、可撤销和可编辑，不能过早伪装成正式计划。
32. 学习路径需要可视化呈现当前主线、起点变化、历史分支、暂停方向和可恢复位置；改变起点创建可追溯分支或版本，不覆盖历史，也不把所有消息和细碎任务都平铺成图节点。
33. 路径图只表达长期有意义的路线节点和可追溯分支：计划树负责当前执行组织，学习成果图负责能力与证据，对话分支负责讨论来源；四者通过稳定引用关联但不互相替代。AI 可以建议切换或恢复，正式改变当前主线必须由用户确认。
34. 执行结构采用“计划 -> 可嵌套学习模块 -> 学习行动”，学习成果作为独立对象与执行树关联；不再把“科目 -> 主题 -> 任务”作为所有计划都必须遵循的固定层级。
35. 允许为新领域模型进行破坏性重构：旧 UI、旧 API 和旧固定层级不再构成兼容约束；但破坏性代码/模型更新与删除用户数据是两件事，任何默认数据库变更仍须经过备份、校验和明确确认。
36. 学习模块是可选容器，计划可以直接拥有任务；模块只在有组织复杂度时出现，并可嵌套，不为形式完整而强制创建空模块。
37. 新委托机会不能按消息持续调用模型检测；采用事件门控、复用当前 Agent、会话边界批量判断和有条件计划复盘。检测可自动，正式创建仍需用户确认。
38. 学习委托允许多个同时开放；界面只突出一个当前焦点，默认同一时间只运行一个实际学习会话。并行开放不等于并行计时或多个 Agent 同时向用户推进。
39. 新委托依据“是否构成独立学习承诺”判断；同一目标下的复习、重试、延迟验证和小幅契约更新留在原委托，独立目标/范围/工具/权限/时间承诺或用户明确要求单独管理时创建新委托。
40. 学习委托生命周期采用“待开始 / 推进中 / 已暂停 / 已结束 / 已取消”；当前焦点和学习会话独立建模，默认同一时间只运行一个实际学习会话。
41. 并行委托先区分可协同的关联与真正冲突，再按信息提示、软冲突、硬阻断处理；内部同时记录确定性和实际影响，预测性问题应在最接近决策的时刻提醒，只有确定性的不可能或不安全操作才阻断具体动作。
42. Nautilus 偏向用户自主和并行探索；系统优先复用跨委托资料、成果和证据，不为了结构整齐自动暂停、合并、关闭或删除委托。
43. 模型策略由用户选择；Nautilus 只能建议升级模型，不能未经确认自动切换。主动升级建议必须允许用户关闭；模型能力、思考强度、人格、学习模式和工具权限彼此独立。
44. 模型策略允许在全局、计划、任务和单次对话中逐级覆盖；本次运行使用的有效配置需要冻结并可追溯，覆盖不能扩大权限。
45. 模型能力登记必须同时描述输入和输出模态，并区分原生支持、经适配处理、明确不支持和未验证；文件容器不等同于原生模态支持。
46. 当前产品讨论优先构想 Nautilus 的长期终局形态，第一位真实用户是产品作者本人；不以旧实现兼容或当前分期成本限制愿景讨论，但仍必须区分愿景、规范和实际实现，并保护用户数据。
47. Nautilus 采用计划/任务工作轴与学习成果长期真相轴的双轴模型；用户从计划和任务进入工作，Core 以学习成果归属证据和学习状态，学习路径与显式关系连接两轴。
48. 学习成果采用“综合成果 -> 可验证成果 -> 版本化达成标准”的分层模型；可验证成果使用稳定的可观察能力身份，不把知识点、任务或不同深度标准复制成多个同名成果。
49. 学习状态只能由具备可追溯依据、指向成果/标准版本/支持维度的证据主张派生；AI 评价本身不是证据来源，无引用判断只能作为推断或未知，不能升级成果状态。
50. 不使用全局证据权重或掌握百分比；版本化达成标准按能力维度声明可接受证据、最低组合和回访条件，证据只在实际产生的情境与证明范围内生效。
51. AI 证据主张采用分层采纳：机械事实自动生效，带引用的 AI 语义主张自动留痕并可形成初步支持，高影响稳定状态需要独立验证或人工复核；没有引用的 AI 印象不能进入证据链。
52. 证据主张的审查生命周期与状态贡献分离建模：审查状态用于可追踪、可质疑、可撤销和可替代；证据适用性与成果维度状态由 Core 根据当前达成标准、证据条件、时间和冲突重新派生。原始产出保持不变，用户认可不能把薄弱证据直接变成稳定掌握。
53. 证据主张采用保守的状态转换和事件驱动批量复核：机械事实和确定性验证可自动采纳；AI 语义主张默认形成候选/初步支持；用户质疑立即移出当前计算但不删除原始产出；撤销表示主张无效，替代表示由新主张接替；标准版本变化由 Core 派生适用性，不把旧主张自动判错；高影响变化、冲突、权限、隐私和费用事项需要在决策附近提示，其余观察可只留审计并在复核卡中汇总；用户界面使用自然语言而非内部枚举。
54. 全局 Agent 采用主动但受控的权限申请：默认只读最小跨计划摘要，发现上下文不足时必须通过 Core 向用户说明目的、范围、内容粒度、时效和替代方案，申请一次性或有限授权；授权只扩大读取范围，不扩大写入、委托或事实确认权限；申请、批准、拒绝、过期和撤销均可审计，拒绝后不得猜测未授权内容。
55. 成果维度状态按版本化达成标准的能力维度和最低证据组合派生，不使用掌握百分比、全局权重或模型置信度；采用主要状态加原因标签，区分未知、依据不足、初步支持、存在不同表现、待回访和支持；帮助条件、独立程度、情境和时间约束不可外推，矛盾证据不抵消，原始记录不因状态重算而改写。
56. 人工复核采用上下文触发的复核卡与全局待处理入口，不做逐条审批收件箱；同质、低风险且无冲突的主张可批量处理，但每条仍独立审计并可撤销；矛盾、隐私、权限、费用、路线、委托和标准变化等高影响事项必须明确提示；用户动作使用自然语言并保留“暂不处理”。
57. 目标与计划在领域模型中语义分离，但界面渐进披露：日常以计划和任务为入口，不强迫用户先维护独立目标层；多计划、路线切换、长期回顾或跨计划成果出现时再显式展示目标中心；没有稳定目标的计划可以先开始，目标、成果和计划不得互相混淆。
58. 目标解释卡的字段和示例只是内部信息结构，不是固定问卷话术；必须保留用户原始表达，向用户展示少量自然、简洁、结合上下文的结果描述，并将来源、假设、证据要求和内部状态按需展开。真实文案不得机械罗列内部枚举或让文案生成偷偷改变目标范围、完成标准和证据归属。
59. 首个领域知识包采用窄领域示范策略：优先来源稳定、关系可审查、验证方式明确并清楚声明范围和限制，不追求一开始覆盖通用知识；包外 AI 推断只能作为临时假设，知识包版本更新必须保留旧版本和争议，不得静默改写证据归属。
60. 学习教练、计划 Agent、任务 Agent 和 Research Agent 共享统一 Agent Runtime；角色契约、数据范围、工具授权、沙箱、预算、超时、审批和审计共同构成一次完整执行环境。能力插件提供受控工具，先实现哪个工具属于工程实施顺序，不是新的 Agent 模式或终局产品决策。
61. Nautilus 的服务对象扩大为任何希望在深度学习过程中获得持续帮助的用户，不再把考研设为首要服务场景，也不按考试、学科或职业身份排列用户优先级；“深度学习”仍是产品边界，考研、编程、专业学习和职业转型只是具体场景示例，不代表核心承诺扩展到一次性问答或机构教学管理。
62. 首个纵切片只有预先审核并版本化的窄领域达成标准包可以参与状态派生；用户提供的可追溯标准在纳入标准包前只能作为候选来源保存。没有合格标准时仍可保存会话、原始产出和事实事件，但不得生成证据主张或学习状态，且标准缺失原因必须可审计。
63. 首个纵切片采用两个连续验收门：先独立验收委托、标准绑定、会话、文本产出、事实事件、关系型投影和回放组成的事实闭环，再在事实闭环通过后验收候选主张、状态派生、复核、质疑、撤销和证据回放组成的证据闭环；不得用证据门的结果掩盖事实门的问题。
64. AI 不可用、超时、取消或输出不合格时，学习会话和原始产出仍必须保存；只记录分析失败，不生成空主张、伪造主张或学习状态。失败不等同于“依据不足”。用户可以重试、请求人工复核或安排补充验证；重试必须幂等，失败与成功运行均可审计，人工复核仍受原始依据、达成标准和 Core 状态派生规则约束。没有合格标准时不启动状态分析。
65. 首个纵切片直接使用新领域模型独立验证；旧 `learning_goal / subject / topic / task` 固定模型、旧任务/计划入口、旧数据语义及其兼容映射、双写和适配层均不进入首片，也不构成未来兼容要求。用户历史数据保护通过备份、校验、恢复和授权规则处理，不通过兼容层延续旧模型。
66. 首片事件账本必须具备最小回放不变量：事件全局唯一、聚合内顺序单调；命令幂等键能防止重试产生重复事实并拒绝同键异请求；事件与当前态投影同事务提交；投影按位置和顺序应用并报告缺口；重建在隔离位置完成、校验后原子切换且失败不覆盖现状；派生状态不能成为事实源；事件版本必须显式升级或拒绝重建；回放需校验数量、顺序、投影版本和关键领域约束。
67. 原始产出与事实事件是两个不同对象：原始产出保存不可篡改的内容，关联事实事件记录何时、由谁、通过哪个学习会话和动作产生该产出；基于产出的证据主张必须同时引用具体产出和关联事件，首片文本产出的候选主张均须满足。计时、会话等独立事实事件不需要人为补造产出；具体字段、表结构和 API 留待工程规格。
68. 事实纠正不覆盖原始产出，而是追加更正事件或新版本；依赖被更正事实的证据主张保留审计历史但移出当前状态计算，相关成果状态和回访队列由 Core 重算。经授权的隐私删除采用内容不可恢复的强删除/不可逆脱敏语义：依赖被删除内容的主张立即失效并触发重算，缓存、索引和普通备份不得恢复已删除内容，只保留不含私人内容的最小审计元数据。
69. 首片必须验收已确认的权限与 AI 失败规则：覆盖跨身份及同一用户内部范围隔离、全局 Agent 最小可见范围、主动申请及拒绝/过期/撤销、拒绝后继续保存、复核卡权限限制和 AI 失败后的保存与恢复入口；Core/Runtime 校验和用户流程均需通过。该项落实既有原则，不重新定义权限模型，详见第 10.8 节。
70. 首片采用测量契约而非预设业务目标值：产品价值指标包括中断后正确恢复委托比例、复核到下一行动完成率和证据可追溯率；无依据主张率、指定 AI 故障场景的产出保存成功率、事件重建一致性、权限违规和隐私泄露是不可被其他指标抵消的硬性护栏；用户质疑率、暂不处理率、无标准降级比例、重试率和人工复核请求率只作诊断。先建立真实使用基线，零分母、窗口未满和无样本单列，具体字段和报表留待工程规格。
71. 需求必须同时标记性质和交付范围：性质为跨阶段不变量或具体功能；范围为事实门、证据门、后续或暂缓。不变量可以与首片范围同时成立，终局功能不能因写入正文而自动进入首片；“待工程规格分解”是准备状态，不是优先级。首片需求使用稳定编号，工程规格和测试引用编号，当前索引见 PRD 第 11.6 节。
72. 产出动作分为普通删除、撤回和彻底删除：普通删除是易用且可恢复的软删除，撤回只让产出退出当前证据计算，彻底删除才是不可逆的内容清除；三者均保留可追溯影响并触发必要的状态重算，事实纠正仍通过追加版本表达。

- 学习起点在稳定前保持低承诺、可撤销和可编辑，不能过早升级为正式计划或把已有证据自动清零。

### 2026-08-24（灵活执行树与独立成果图确认）

- 用户确认不再把固定“科目 -> 主题 -> 任务”作为所有学习计划的通用层级。

- 用户明确表示不需要为旧版本保留产品或 API 兼容，允许直接重做新的领域模型和相关实现。
- 正式明确：允许破坏旧 UI、旧 API 和旧固定层级，但不等于可以未经确认删除已有学习内容；默认数据库变更仍需备份、演练、校验和恢复路径。
- 用户确认学习模块为可选容器，计划可以直接拥有任务；模块只在需要组织复杂度时创建或嵌套。

### 2026-08-24（模块可选与破坏性重构边界定稿）

- 用户确认模块可选：计划可以直接拥有任务，模块仅在有组织价值时出现并可嵌套。
- 用户确认不为旧版本保留产品、API 或固定层级兼容；后续可以直接按新领域模型破坏性重做。
- 明确破坏性代码/模型更新不等于删除用户数据；默认数据库变更仍需备份、隔离演练、完整性校验、恢复路径和明确授权。

### 2026-08-25（四类用户管理对象确认）

- 用户确认学习模块也属于用户直接管理的对象，不只是系统内部的组织容器。
- 正式明确：计划、学习模块、任务和学习委托都是用户拥有、可查看、可调整、可暂停或可确认关闭的长期对象；它们的管理粒度不同，但不能由 AI 未经确认静默改变。
- 计划负责学习承诺与范围，模块负责组织，任务负责可执行学习行动，学习委托负责一次长期协作的目标、完成契约和工作边界。
- 计时、学习会话、事实事件、证据、进度和掌握状态仍由 Core/Runtime 根据实际行为派生，不能因为对象由用户管理就允许手动伪造客观状态。

### 2026-08-25（委托候选检测时机原则确认）

- 用户确认不能每时每刻或逐消息调用模型检测新委托，成本控制本身是产品和 Runtime 约束。
- 正式采用“低成本事件记录 -> 复用当前 Agent 输出信号 -> 会话边界批量判断 -> 有条件计划复盘”的检测层次。
- 用户明确提出独立安排、当前工作无法继续、权限/费用/范围发生高影响变化时可以即时提示；普通非阻塞信号延迟到自然停顿或会话结束。
- 正式创建学习委托仍需用户确认；具体预算、冷却时间和批量阈值需通过真实使用与成本测试确定，当前不使用未经验证的固定数字。

### 2026-08-25（学习委托并行模型确认）

- 用户确认多个学习委托可以同时开放；界面只突出一个当前焦点；默认同一时间只运行一个实际学习会话。
- 正式采用“独立学习承诺”作为新建条件：同一目标下的复习、重试、延迟验证和小幅契约更新不新建委托；独立目标、范围、工具、权限、时间承诺或用户明确要求单独管理时创建新委托。
- “开放委托”“当前焦点”“进行中的学习会话”是三个不同概念，后续状态模型不得合并为单一状态字段。

### 2026-08-28（并行委托关联与冲突原则确认）

- 用户确认并行委托采用“信息提示 / 软冲突 / 硬阻断”的处理结果，但系统必须先区分可协同的关联与真正冲突。
- 冲突判断同时考虑确定性和实际影响；预计时长、未来负载等预测不能伪装成事实，应在最接近实际决策的时刻提示。
- AI 负责发现潜在关联、解释影响和提出选项；Core 负责单会话、固定时间、权限、独占资源和事实写入等确定性约束。
- 系统偏向用户自主和并行探索，只阻断具体不可能或不安全的操作，不自动暂停、合并、关闭或删除委托。
- 本轮仍是产品设计记录，尚未实现新的冲突对象、Runtime 规则或用户界面。

### 2026-08-28（模型策略由用户选择）

- 用户确认模型策略由用户自行选择，Nautilus 只能根据任务情况提出升级模型的建议，不能未经确认自动切换模型、Provider 或策略。
- 用户可以关闭主动升级模型建议；具体默认开关状态、提示时机和频率仍待设计。
- 正式区分模型策略与思考强度：模型策略决定能力层级，思考强度只调节单次运行投入，二者不能互相替代。
- 人格 Profile、学习模式、模型策略、思考强度和工具权限必须分开管理；选择更强模型不能扩大 Agent 权限或绕过 Core/Runtime 约束。
- 本轮仅确认产品边界，尚未实现模型策略预设、能力登记、升级建议或思考强度参数映射。

**当前实现边界与未完成方向**

- 当前实现只在 Provider 自身具备相应能力时允许其提供来源 URL，并拒绝明显虚构或不合法的 URL；系统没有独立开放 Web Search、任意网页抓取或开放网络 Agent。受控来源检索仍需单独的 Research Agent 工程规格和授权边界。
- 当前用户材料支持文本粘贴和浏览器可读取的文本文件，不扩展复杂附件解析；验证材料的完整彻底删除生命周期仍需后续工程规格。
- 本轮实现了验证尝试、答案隔离、失败重试和任务完成事务保护，但尚未把验证结果接入完整的证据主张/成果状态派生，也尚未实现完成后的计划复核卡、统一回归教练视图或真实使用基线。

### 2026-09-16（审查建议采纳与验证可靠性优先）

- 用户在阅读 09-16 审查结论后确认“先按照你的意思来改”，采纳推荐顺序：同步规则，优先验证可靠性与启动迁移保护，再接证据/删除链、最小复核和返回入口、真实使用基线，最后评估完整成果图/路径图。
- 作答先持久保存，评估绑定不可变提交；最终确认是评估完成后的独立操作，绑定具体提交、评估和契约版本，不再次调用模型。
- 同一行动有多个委托时，完成本次验证只完成本次委托；其他 ready/active/paused 委托保留，行动继续 open。最后一个开放委托满足验证、停止条件及用户确认后才自动完成行动；不批量关闭其他委托。成果是否有支持证据仍独立派生。
- 普通服务启动不包含数据库初始化或迁移授权。缺库或版本不匹配时停止，指定库的检查、备份、升级及服务启用继续单独授权。
- 第一实施段覆盖保存/评估/确认/恢复、结构和来源校验、学习室对话归属及启动保护。证据/彻底删除、指标修正和最小计划复核属于已采纳的后续顺序，不能因决定确认就写成已经实现。
