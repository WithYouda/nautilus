# Nautilus PRD、实施计划与当前代码对照审查

日期：2026-09-16，Asia/Shanghai。

本轮为审查与建议，不实施业务修复、不批准新的产品语义。依据根目录 AGENTS、PRD V2、原始技术基线、当前产品决策、首片实施计划与记录、两份最终验收记录及生产学习库操作记录；重点核对 021/022、新领域学习入口、验证、恢复、指标与启动路径。历史测试结果只说明当时的验收范围，不作为当前所有新增能力的通过证明。

## 1. 判断

PRD 的长期定位、双轴模型、事实与证据分离、标准准入、用户确认和两个连续验收门仍然成立，没有发现需要推倒重来的产品架构问题。但文档尚未同步最新验证语义，后续计划的依赖顺序需要调整，当前 022 也尚未达到可安全交付真实使用的闭环标准。

## 2. 文档与计划问题

1. **最新验证规则没有进入正式需求和任务验收表。** 决策记录 2026-09-14 已确认教学与验证分离、最后确认和完成后的计划复核，PRD 与实施计划仍主要描述原始产出分析和补充验证安排。建议把已有确认同步为明确的增量要求，不重新讨论已经确定的方向，不重开旧验收门。
2. **旧完成规则仍可能误导实现。** 决策记录第 8.2 节仍写“用户可以声明完成且不再验证”，第 14.11 节仍有将计划描述为“为什么学、最终结果”的早期表述。应按最新要求注明适用范围：结束/暂停会话、关闭委托、验证后完成新领域行动和成果获得支持分别表达；已有旧计划的记录型入口继续保持其原有边界。
3. **图形界面被设为核心连续性的前置依赖。** 实施计划 Task 17A 依赖 Task 16，而 Task 16 又依赖成果图。最小的当前位置、证据、未知与下一步卡片可以直接使用现有对象和事实，无须等完整图形界面。建议提前交付最小恢复和计划复核，把完整图、主动后台运行和自适应排期留在后面。
4. **当前状态与历史快照混在一起。** 进度首页曾停留在 09-13，底部已有 09-14 验证；生产记录顶部仍说默认主库未迁移，第 7.1 节却记录启动时应用 005-010。架构规格仍使用早期 delegation draft 状态，并未在正文同步已记录的同事务回放替代。建议保留历史记录，只把一个简短的当前快照作为交接入口；不能用旧数据库版本和旧服务状态指导本次运行。

## 3. 当前代码的高优先级问题

### R1：验证提交没有先保存，重试还会覆盖原始作答（P1）

依据：`backend/app/verification.py:249` 先调用 Provider，`:314` 才更新 `submission_json/result_json`；提交请求没有独立幂等键，更新条件只有旧 status。

隔离 Mock 诊断确认：

- Provider 返回非 JSON 后，验证仍为 ready，submission_json 为 NULL；失败审计不能恢复本次作答。
- failed 状态下两次并发重试都能成功，旧请求晚返回时覆盖较新的回答和评估。
- 成功重试也覆盖此前作答；多条审计只记录状态，不保存对应的提交版本。

这直接偏离 PRD 的 AI 失败不阻塞保存、原始产出不可改写及可追溯要求。建议复用现有原始产出/事实机制，按提交追加版本，评估绑定提交 ID；先保存再分析，幂等重试不重复事实，迟到结果不覆盖新提交。只补所需的提交记录和命令，不建设通用作业框架。

### R2：停止条件确认发生在评估之前，确认还会重新评分（P1）

依据：`frontend/src/LearningVerification.tsx:166` 在作答时显示停止条件勾选，`:186` 在未勾选时禁用提交；`backend/app/verification.py:232` 只对 passed 提前返回，submitted 会再次调用 Provider。

实际影响：用户必须先宣称满足停止条件才能请求评估，无法自然完成“先验证、看结果、最后确认”。后端隔离诊断还确认：首次评估通过且停止条件满足但未确认，第二次仅补确认会重新评分，甚至把原成功结果改为 failed。

建议采用明确的顺序：保存作答 -> 评估结果 -> 停止条件核对 -> 用户确认完成。确认绑定已保存的评估及契约版本，重复确认幂等且不调用模型；用户修改作答时才产生新的提交与评估。这是落实 09-14 已确认方向。

### R3：同一行动的多个委托与自动完成规则不相容（P1，处理规则待确认）

依据：`backend/app/core/events.py:314` 将整个 action 设为 completed，但只关闭指定 delegation 及其 running session。

隔离复现：同一行动有 D1、D2，D2 正在学习；D1 验证通过后，action=completed、D1=completed，但 D2=active、D2.session=running。D2 此后无法启动新会话。

建议：完成确认只处理本次承诺；还有其他开放委托时保持行动可继续，并在计划复核中说明剩余承诺。单委托满足全部条件时自动完成行动。这个规则涉及“一份委托达成是否足以完成整个行动”的产品取舍，尚未确认，本轮不实施，也不能自行改成批量关闭全部委托。

### R4：普通启动仍会自动迁移真实数据库（P1）

依据：`backend/app/main.py:48` 创建默认 Database，`:54` 调用 open_learning_database；`backend/app/learning_storage.py:37` 无条件创建允许应用全部 011+ 的 Database；`backend/app/db.py:30` 构造时直接迁移。独立升级工具的 authorized 检查未覆盖这条启动链。

实际影响：只授权启动服务时，待应用迁移也会被执行。历史生产记录已记录过主库启动时应用 005-010；本轮不重新执行该操作。

建议普通生产启动只验证 schema 是否可运行；升级必须走指定数据库、备份、显式授权和校验工具。隔离测试可显式启用建库/迁移。无需引入额外部署平台。

### R5：验证和教学的恢复仍依赖页面临时状态（P1）

依据：`frontend/src/LearningVerification.tsx:21` 起的 verification、responses、material 均是组件状态；返回教学再进入会重新挂载，没有读取 GET /verifications 恢复当前尝试的逻辑。`:42` 的请求键仅含 action 与 mode，而后端请求指纹还包含 delegation/session；同一行动的新会话或另一个委托会发生幂等冲突。

新领域对话也仍以 independent 范围复用旧对话服务；`frontend/src/AiLearningRoom.tsx:488` 恢复主要依赖 sessionStorage 和 scope/target，没有持久化 action/delegation/session 与 conversation 的结构关联。`frontend/src/FactWorkspace.tsx:1192` 的当前会话卡说明可回学习室，但实际只有结束记录按钮。

建议把当前验证 ID、提交和新领域教学对话的归属持久化，重新进入先恢复已有对象；新的验证尝试才生成新幂等键。独立 URL 可以后做，正确恢复是当前关键旅程要求，不能归为纯 UI 细节。

### R6：指标会把会话结束当成下一行动完成（P1）

依据：`backend/app/measurements.py:236` 的复核指标把同一 action 后续任一 ended_at 非空的会话计入完成，包含 interrupted；`:215` 以中断后的任意首次会话推断恢复意图；`:75` 对产品比例直接用 100% 判断 pass/fail。

这些与 PRD 11.5 的下一行动完成事实、主动切换单列和先采基线再定目标值不一致。当前报表也未覆盖 022 的验证提交保存失败，因此原“AI 失败保存成功率”不能扩展解释为验证模块同样受保护。

建议以显式 follow-up -> 下一行动关联和 action.completed 事实计数；未有足够事实时标未测，主动切换/意图未知单列。产品基线展示分子、分母和未知，不先设 100% 的业务通过线。此项应在正式解释 Task 13B 报表前修正；不妨碍先记录用户自然使用中的问题。

## 4. 其他需要一起收口的边界

- **结果结构校验（P2）**：verification.py:291 把任意 feedback/next_step 对象 str() 后公开。Mock 诊断确认嵌套 answer_key/private_material 对象会被字符串化返回。应严格要求文本类型、拒绝额外结构；正常顶层答案白名单已存在。结构校验不能保证任意模型文本都绝不复述答案，不作此承诺。
- **来源宣称（P2）**：verification.py:149 只检查 http(s) 前缀，诊断接受 `https://` 和明显 example.com 占位来源。应校验 hostname、拒绝明显占位链接，并说明是 Provider 提供且未独立核验的来源；不需要新增抓取或 Web Search。
- **证据接入与删除（已知未完成）**：022 独立保存验证材料，没有接入 raw artifact -> fact event -> claim -> derived state，也没有对应彻底删除流程。建议复用既有事实、证据及删除链，避免长期维护另一套用户产出存储。无合格标准仍只保存验证记录与反馈，不派生能力状态；AI 自拟通过标准不能直接成为已审核标准。
- **审计快照（已知未完成）**：验证未冻结契约/标准版本及实际 Provider 模型来源。应随提交评估记录必要快照，沿用已实现的运行追溯原则。

## 5. 推荐的具体推进顺序

以下是本轮建议，尚未成为已批准的新排期：

1. 同步已有确认的验证规则与验收条目，标出多委托完成规则这一项尚需产品确认的取舍。
2. 完成最小“验证可靠性收口”：先保存、不可变提交、幂等与并发、结果后确认、恢复、私密字段校验及迁移启动保护；新 schema 从 023 起追加。
3. 接回现有事实、证据与删除链，先用已审核 Python 正则标准验证；普通无标准学习继续明确降级。
4. 提供最小完成后/返回时复核卡：当前位置、已有依据、未知、一个推荐行动及理由、继续入口；新增或修改正式计划仍需用户确认。同步纠正上述指标口径。
5. 经用户授权检查真实库实际版本、备份、迁移及启用后，完成真实的学习 -> 验证 -> 确认 -> 离开 -> 返回 -> 下一行动旅程，采集真实使用基线，再评估成果图和路径图优先级。

下一开发轮建议先落实第 1-2 项。多委托完成规则应在实现该分支前确认，不影响其他已确认不变量的修复准备。本轮没有启动这些业务修改。
