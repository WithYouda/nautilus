## 1. 方向与产品价值

**一句话定义：让 Nautilus 根据当前学习目标、知识难点及学习者的实际理解情况，选择或生成可操作的教学界面，让用户通过预测、操作、解释和验证来学习；而不是只把 AI 回答换成花哨的卡片。**

作者于 2026-10-10 明确认可该方向与“长期、深度、可验证学习”的契合度，认为它可能成为 Nautilus 的重要竞争差异及对外卖点，要求写入项目长期规划。这里确认的是**方向与研究优先性**，不等于批准立即开工、追加当前阶段交付范围或采用某一框架。

可供后续产品定位使用的价值表达（**候选文案，未经对外验证**）：

> 不只是让 AI 解释知识，而是让 AI 为你创造理解知识的交互环境。

实际差异化不在“能生成界面”本身，而在**生成的交互能否根据学习困难变化，并进入 Nautilus 原有的可追溯学习闭环**。长期保存、复习和正式验证能力比单次炫酷演示更重要。

## 2. 用户旅程：从读解释到做实验

推荐的主流程：

1. 学习者提问，或在当前教学流程里出现可以明确定位的理解障碍。
2. 现有教学运行时结合本轮意图、教学模式、已确认学习偏好、实际学习情况与获准资料范围，判断文字讲解是否足够，以及哪种交互形式更适合。默认不强制生成 UI。
3. 系统优先复用现成教学组件；仅当现成组件明显不足时，才考虑在隔离环境中按需生成新交互。
4. 学习者**先预测、再操作、再解释**；不应把一张动画当作已经学会的证据。
5. AI 用实际操作与解释作针对性反馈，并支持追问、纠错、继续练习或返回原教学步骤。
6. 有意义的学习产出按原任务/对话/回答版本保存、回看；需要证明掌握时仍走既有正式验证与证据审查流程，而不是根据操作次数自动认定掌握。

### 首批高价值教学场景（候选）

| 场景 | 动态界面 | 学习者真正做什么 | 与现有能力的衔接 |
| --- | --- | --- | --- |
| Softmax / 概率分布 | 可调温度、实时柱状图、候选概率对比 | 预测温度变化，再拖动、解释概率变化 | 分步教学、复述、变式练习 |
| 牛顿第二定律 | 力/质量滑块与运动模拟 | 预测加速度、改变参数、解释错误直觉 | 苏格拉底追问、针对性反馈 |
| 排序或图搜索算法 | 逐帧执行、输入数据修改、关键步骤高亮 | 预测下一步、观察差异、自己复述算法 | 项目实践、代码教学与学习记录 |
| Obsidian 知识笔记 | 与获准原文关联的概念图或交互解释 | 从自身笔记出发探索关系，回看出处 | 已有知识库来源/片段/版本追溯 |

优先探索能验证教学价值的“理解预测—操作—复述”场景，不以 3D、小游戏或视觉效果数量作为第一目标。

## 3. 与 Nautilus 现有系统的关系

本能力应作为**教学呈现与交互层**接入既有功能，不另外建立一套 AI 学习产品：

- **C1/C2 教学运行时**：继续决定当前教学模式、步骤、帮助程度和实际理解情况；生成式 UI 只负责选择适合的呈现及交互，不能绕过步骤/尝试/纠正与中断恢复语义。
- **学习室与题目讨论**：复用当前任务归属、消息/回答版本、分支及返回路径；互动内容必须能够说明自己对应哪个知识点、哪一次回答。
- **B1/B2/B3 资料链**：只读取用户当前批准的笔记、知识库或附件范围，保留来源与版本；生成的视觉解释不能冒充原始文献，也不能因展示方便而扩大资料范围。
- **D1 成果/证据与 Core**：交互参数、用户解释、预测和练习输出可形成原始产出与候选学习观察；只有通过现有证据规则和审查，才能影响可信学习状态。
- **C3 模型策略与权限**：继续使用 Nautilus 已选择的 Provider、模型与运行快照；不静默切换模型、提高权限或向外部服务发送私文。

交互作品应是**可回看、可继续的学习产物**，不只是一条短暂渲染出来的聊天回复。其业务身份、持久化及版本化方式须另做工程规格后再实施。

## 4. 建议架构：受控组件优先，隔离生成作为扩展

```text
用户请求 / 实际学习障碍
        ↓
现有 C1/C2 教学运行时（意图、教学步骤、获准资料、模型配置）
        ↓
交互呈现决策：纯文字 / 预制组件 / 定制沙箱交互
        ↓
界面描述与来源快照 → Schema 校验、权限/预算检查
        ↓
React 渲染器（可控组件目录）或隔离沙箱
        ↓
用户预测、调整参数、提交解释
        ↓
可追溯交互产出 → 现有教学反馈 / 原始产出
        ↓
如需证明掌握，仍使用现有正式验证和 Core 证据链
```

**优先方案（待 PoC 验证）**：基于现有 React 19 + Vite 前端、Python 后端，先引入一个受控的教学组件目录，例如参数滑块、分布曲线、步骤播放器、关系图、问答/预测卡。让 AI 返回结构化 UI 描述与初始参数，由应用自己的组件渲染。参数拖动、公式计算、动画播放等高频操作尽量在本地完成，不因每次交互重新调用大模型。

**可选增强**：对于组件目录覆盖不了的知识内容，借鉴 CopilotKit **Open Intelligent UI** 的按需界面生成与沙箱思路。但它目前是独立的 Next.js/CopilotKit + Python Agent 示例应用，**不是可以原封不动嵌入当前 Vite 项目的完整功能模块**。需要验证复用其协议/渲染/沙箱能力的实际改造成本、许可证、性能和权限约束；不要为集成而替换 Nautilus 现有运行时。

框架候选及角色（2026-10-10 调研记录，实际选型以 PoC 为准）：

| 候选 | 借鉴点 | 初步判断 |
| --- | --- | --- |
| [CopilotKit Open Intelligent UI](https://github.com/CopilotKit/OpenIntelligentUI) | 任务驱动选择文本、原生组件或隔离运行的自定义交互 | 重点体验与研究对象；不直接替换现有产品 |
| [A2UI](https://github.com/a2ui-project/a2ui) | 跨端的声明式、流式 UI 协议与受控组件映射 | 适合长期多端方向；版本、渲染器成熟度待核实 |
| [Vercel json-render](https://github.com/vercel-labs/json-render) | 按组件目录和 Schema 生成 React UI | 适合低成本验证受控组件方案 |
| [AG-UI / CopilotKit](https://github.com/CopilotKit/CopilotKit) | Agent 与前端状态、事件及交互通信 | 视现有 Runtime 集成成本选用，不必强制一起引入 |

当前 A2UI 文档将 v0.9.1 标为生产版本、v1.0 标为候选；选型时应重新核查兼容性。上述项目提供的是实现参考，不构成作者已经批准的依赖清单。

## 5. “交互式学习作品”概念与数据原则

建议暂用 **Interactive Learning Artifact（交互式学习作品）** 作为产品/领域设计工作名，不提前决定数据库表名或 API。

后续设计至少要分清三件事：

1. **作品定义**：界面类型、可复现的组件/代码版本、初始数据、明确来源及版本、生成时的任务/消息/模型/权限边界。
2. **一次操作过程**：实际调整过的参数、用户预测、解释、练习提交、反馈与停止位置；失败、取消和未完成不能变造成功学习事件。
3. **证据或学习状态**：用户作答与作品操作可作为原始记录，但不能越过 Nautilus 现有正式验证、候选审查和能力状态派生机制。

要求可关闭重开、恢复当前步骤、区分旧/新版本、从历史消息或分支准确回看。保存结构化作品而非仅存一张截图；当旧沙箱代码已不可安全执行时，应能保留解释、输入和结果的可读回退视图。

跨设备同步沿用后续客户端统一架构，不单独引入另一套同步系统；正式删除、撤权、备份和恢复屏障须覆盖作品、操作数据及受管理的派生副本。

## 6. 关键质量与安全边界

- **教育正确性**：数值公式、图像刻度与仿真参数必须可校验；能用确定性计算/测试的结果不要完全依赖模型自由编写。错误动画会直接误导学习。
- **隔离执行**：任意生成的 HTML/JS 如获准启用，必须在严格隔离的执行环境运行；默认无文件、知识库、任意网络、凭据和核心数据库权限，只允许白名单交互事件通过受控桥接进入宿主。不能把“iframe”本身当作完整安全保证。
- **外发权限**：沿用 A2 私文外发逐次授权、B 阶段资料范围以及 E4 插件权限边界；第三方沙箱、生成服务或可视化服务不默认获得私有资料。
- **权限与事实**：UI 中的点击、拖动和模型推断不产生正式完成/掌握；用户确认、证据审核与 Core 写入权不被新的呈现层改写。
- **稳定性与成本**：模型失效、界面生成失败或脚本崩溃时，原学习会话仍可继续文字教学并保存已有产出；限制生成次数、代码大小、计算时间和资源使用，高频控件尽量本地运行。
- **可访问性与视觉一致性**：支持键盘/触屏、移动端小屏、缩放与无障碍；遵守后续 F 的统一设计系统，默认简洁易懂，不让交互喧宾夺主。

## 7. 推荐验证路径（候选，不改变既定开发阶段）

**P0 — 独立技术验证。** 使用隔离样本验证受控组件渲染与一次自定义沙箱交互；对比 json-render、A2UI 与 Open Intelligent UI 的集成复杂度、流式渲染和安全限制。不触碰真实 Vault、正式数据库或当前 trial。

**P1 — 最小教学体验。** 在现有 Web 学习室的受控实验中先做一个 Softmax 温度滑块（输入、概率图和用户解释）并提供文本回退；验证桌面/手机操作和数学正确性，再补一项物理或算法演示。这个阶段优先测试“互动是否真的提高理解”，不做通用 UI 生成平台。

**P2 — 教学闭环。** 接入现有教学方式和学习观察：识别实际困难 → 推荐互动 → 先预测再操作 → 复述/作答 → 反馈 → 原有验证流程。记录实际帮助条件和来源，不自动生成能力结论。

**P3 — 长期作品与多端。** 经真实体验证明价值后，再设计作品身份、版本、历史回看、存取、清除及客户端同步；最后评估通用自定义交互代码生成是否值得进入正式能力范围。

各阶段是否启动、与 F/E 的具体插入点及资源投入，由作者单独确认；本文件不将 P0–P3 设为当前 A–F 的必做验收条件。

## 8. 真实价值怎样验收

PoC 不以演示数量、图表数量或“生成成功率”作为最终价值指标。推荐对照同一知识点的**普通文字教学**与**交互教学**，记录：

- 用户能否提前预测结果、解释参数关系；对错误理解是否产生有效纠正。
- 相同或近似难度的新题是否能够独立完成；必要时结合延迟回访比较，而不只看演示当场的兴奋感。
- 交互生成与首屏时延、失败回退、单次模型成本、手机操作成功率。
- 学习记录/作品回看是否准确归属任务与资料版本，取消/删除/撤权后是否仍满足原安全边界。

先收集作者真实体验与可重复样本，再判断是否扩大范围；外部推广口径不提前声称能提高学习效率或掌握率。

## 9. 待设计时必须明确的问题

- 首批服务哪些知识类型？优先数学/物理/编程，还是先满足作者当前实际学习任务？
- 交互生成是学习者主动点选、AI 提议后确认，还是特定条件下自动展示？如何控制打断频率与费用？
- 第一版作品需要保存到何种程度：只保存可回看结构，还是连操作历史与重播一起保存？
- 先仅 Web 试用，还是要求第一片同步覆盖 Android/Windows？触摸和断网恢复需求如何验收？
- 选择 A2UI/json-render/原生目录，是否真的需要额外 Agent 通信框架？自定义沙箱何时允许进入生产？
- 哪些学习行为只是一种练习/观察，哪些可以经过现有验证流程进入正式证据？

这些问题属于未来实施规格的决策，不由本次“把重要方向写入规划”的授权自动回答。
