# D1 成果关系、成果图与证据覆盖：实施计划草案

日期：2026-10-04。状态：供作者审阅，尚未批准具体实施方案；本轮不改应用、数据库或试用服务。

依据：PRD V2 5.2、6、8.5、9、11.2，产品决定4.5、5、17.7–17.8，以及当前路线D1。已确认的原则与下述实施建议分开；批准阶段方向不等于批准未决交互。

## 1. 交付目标

用户可以把长期希望达到的综合能力与已有可验证成果关联起来，看到哪些方面已有支持、哪些有不同表现、哪些仍未知，并从图中直接回到原始作答、反馈和标准版本。关系可以调整和撤销，旧证据及当时的判断仍可追溯。

计划树继续说明“要做什么”，成果图说明“能够做什么及依据是什么”。D1不接管任务排序或长期路线，不扩展到D2路径图、D3后台教练、客户端迁移或全站UI重构。

## 2. 已核实的基础与缺口

| 当前基础 | 本次复用方式 |
| --- | --- |
| `learning_outcome`已保存对象、行为、情境、来源和稳定ID；创建走Core命令/事件 | 保留所有既有成果身份，不按标题自动合并 |
| 标准包、不可变达成标准版本和可用性记录已存在 | 状态始终指向具体标准版本，不把不同标准混成一项总分 |
| 证据主张、审查、撤回及按维度派生状态已有实现 | 图只读取已有判定和来源，不能自行生成掌握结论 |
| `OutcomeReview`及学习记录入口已有单成果依据回看 | 点成果节点继续使用原始作答/评估/帮助/补练/回访回看 |
| 已有事件回放、删除/清除、恢复保护和owner隔离 | 新关系及必要私文接入同一生命周期，不另建证据档案 |

已核对代码：`backend/app/core/commands.py`、`core/learning.py`、`core/events.py`、`migrations/011_nautilus_learning_domain.sql`、`standards.py`、`state_derivation.py`、`outcome_review.py`，以及`frontend/src/LearningRecords.tsx`、`OutcomeReview.tsx`。

目前未见综合成果组织、成果间正式关系及候选审查/撤销的完整实现，也没有成果图总览。标准包仍是有限的已审核窄领域配置，不能把新增成果都假定为已有合格标准。旧的任务/证据关联可读取展示，不重建为另一套可编辑证据关系。

## 3. 已确认的硬边界

- 综合成果与可验证成果分开；目标、计划、章节或任务名称不自动变为能力成果。
- D1最终覆盖包含、前置、等价、重叠四类成果关系；第一片先做包含关系，后续补齐其他关系，不能以第一片代替整个D1完成。
- AI只能提出关系候选；用户确认才能采用。用户采用只表明个人组织选择，不能把没有可靠依据的推断变成客观硬前置。
- 等价/包含关系不自动迁移、复制证据；图中能展示关联，原始证据目标、标准和版本保持。
- 综合成果不平均子成果状态、不显示伪精确掌握百分比。部分子成果有支持不代表综合能力已成立，整体实践/迁移证据仍单独呈现。
- 无合格标准时展示成果、记录和标准缺口，不派生能力结论；搜索结果、AI建议和点击确认不自动批准正式标准。
- 关系调整、撤销、来源失效和清除不能丢失历史或恢复已清除私文；缺失来源如实显示不可查看，不补造内容。

## 4. 建议的实施顺序

### 第一步：确定关系契约与页面草图

补一份精简工程契约，明确综合成果身份、关系方向/适用情境/来源、修订与撤销、重复关系处理及证据展示规则。包含关系禁止循环；前置关系的方向、循环与冲突处理需在实现前明确，等价与重叠不能被当成有向学习顺序。

核对已有Core命令、事件投影、回放及清除接入点，选择最小数据增量。新结构通过新增迁移加入，既有身份、标准、证据和旧迁移不改写。

提供桌面和手机的简洁页面草图。推荐从“学习记录”增加“成果图”入口，支持按计划筛选、搜索已有成果；跨计划选用保留同一成果身份。默认显示节点和简短状态，关系说明/来源/历史由用户点开。

**产物：** 可审阅的契约及页面草图；尚有产品歧义时先确认，再实现依赖部分。

### 第二步：交付一个可使用的手动首片

完整旅程：创建一个综合成果 → 搜索/选择已有成果或明确新建可验证成果 → 建立包含关系 → 图中查看各成果的证据覆盖 → 点开既有依据回看 → 调整/撤销关系并查看历史。

首片同时包含必要的后端和界面，不先做一个只有表和接口的空架子。复用成果身份，不复制记录；取消关系只改变组织，不删除成果或证据。每项关系有来源、版本、归属和审计，重复保存、旧页面冲突及撤销有明确结果。

图中按实际标准显示已有支持、不同表现、依据不足/未知；“没有合格标准”与“有标准但尚无证据”分开表达。同一成果多个标准不自动选一个代表全部情境。综合成果默认展示子成果覆盖和整体证据缺口，不据子项数量宣布达成。

**可验收结果：** 一个综合成果关联多个已有成果，能够从节点一路回到原始依据；刷新、切换和撤销后身份与历史保持。

### 第三步：补齐其余关系与冲突呈现

加入前置、等价、重叠关系的手动维护、来源/适用范围和历史回看。已有任务→成果、证据→成果的联系按真实引用展示，关系编辑不能覆盖Core的证据判断。

新增/修改关系须校验两个端点的归属、类型和关系约束；明显无效的自指、包含循环或互相矛盾操作不能静默落库。前置关系首版用于说明个人成果组织和依据，不因此自动阻止开始任务或重排计划；涉及D2路线的行为另行处理。

**可验收结果：** 四类关系可辨认、可追溯、可调整；等价关系不会引发自动合并或证据迁移。

### 第四步：接入AI关系建议及必要标准治理

用户明确点击后，AI只对选定成果范围提出候选关系，并给出理由、实际来源和不确定处；提供逐项采用、调整或拒绝。先以已有成果之间的关系建议为范围，不自动扫描所有学习私文、生成整套能力地图或修改正式关系。

默认仅向AI提供用户选定的成果声明与允许读取的必要信息；需要任务私文或证据正文时沿既有授权边界处理。请求冻结输入范围，模型失败、取消、重复提交或来源变化都不能留下伪正式关系。候选建议的私文及其清除接入既有受管理清除/恢复保护。

标准治理只补D1确实依赖的来源、适用范围、版本和审核状态呈现/校验。沿用已审核窄领域包验证链路；新增标准若确有需要，必须先准备可审查的独立标准草案，不把AI关系建议的“采用”复用为标准批准。首版不建设通用知识包市场或批量发布平台。

**可验收结果：** AI建议未经确认不改变图；确认后仍区分个人决定和客观依据；无标准成果不会得到伪掌握结论。

### 第五步：检查、启用与实际试用

聚焦关系版本/撤销/冲突/owner隔离、事件回放、来源清除/受管理备份、标准变化及证据去重；核对普通关系调整不改写旧证据。检查桌面与手机上的创建、连接、筛选、依据回看、失败重试及刷新恢复。

需要迁移时按既有常设授权更新原trial，保留正式升级工具的自动前后备份并核对旧数据；不另建长期试用环境。每个完整首片通过相关检查即可启用并本地提交，不把所有后续优化绑成一次大交付。

邀请作者用一个实际综合成果及已有学习记录走完闭环；工程通过和实际体验分别记录。首片可提前试用，D1结束仍要求后续已定关系、候选审查和证据边界完成。

## 5. D1结束条件

1. 综合成果及四类成果关系有最低可用维护/查看界面，来源、版本、适用范围和撤销可追溯。
2. 证据覆盖按真实标准/维度呈现，能回到原始依据，无标准、矛盾和未知不被隐藏。
3. 关系更改不迁移或重复计入证据，不改变旧版本，也不从子成果自动推出综合掌握。
4. AI候选与用户正式决定隔离，权限、失败/取消、来源失效及清除边界通过检查。
5. 同一原trial可使用完整旅程，桌面/手机检查与实际试用反馈分别记录；再按路线进入D2。

## 6. 本次请作者审阅的建议

- **交付顺序：** 手动包含关系＋证据回看先形成完整首片，再补其他关系和AI建议。
- **界面入口：** 先放在学习记录中的成果图入口，不增加一套顶层工作区；来源和历史按需展开。
- **AI首片范围：** 只为用户选中的已有成果提出关系建议，不自动生成整套成果地图或重新安排任务。

这些是实施建议，尚未视为作者批准。成果关系、证据边界及D1顺序已有正式规范，本计划不重新征求其是否需要；具体技术选型、文件拆分和检查数量由批准后的实现决定，不预设耗时承诺。
