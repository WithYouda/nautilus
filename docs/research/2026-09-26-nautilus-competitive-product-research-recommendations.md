## 1. 调研目的

本次调研不是寻找“功能最多的 AI 学习产品”，而是围绕 Nautilus 当前核心承诺寻找可借鉴的产品机制：

> 用户每次回来时，能够知道自己走到哪里、什么已经被证据支持、什么仍然未知，以及下一步最值得做什么。

因此，本次重点观察的不是单次问答、内容生成或考试刷题本身，而是：

1. 用户如何进入一次真实学习；
2. 学习过程中如何获得恰当而非过量的帮助；
3. 错误或薄弱点如何转换成下一步行动；
4. 中断后如何恢复上下文和学习位置；
5. 学习资料、作答、反馈和验证如何保持可追溯；
6. 一段时间之后如何重新检查过去的学习判断；
7. 产品如何避免把“做过”“看过”“答对一次”误写成稳定掌握。

## 2. 重点调研产品

### 2.1 Heptabase AI Tutor

可借鉴点：

- 围绕学习目标组织结构化、个性化学习会话；
- 用户回到课程时，能够从具体学习位置继续；
- 学习过程比纯聊天更有“正在完成一段学习”的结构感；
- AI 与已有知识资料、卡片和白板上下文结合。

对 Nautilus 的启发：

- 聊天可以是主要交互形式，但不应是用户理解学习进程的唯一结构；
- 学习室可以持续回答“本次要解决什么、当前做到哪里、下一步是什么”；
- “继续学习”应恢复到一个明确学习位置，而不是只恢复一段对话历史。

不建议直接照搬：

- 不把课程目录完成度当作能力掌握度；
- 不因为系统生成了一条路线，就要求后续严格沿该路线推进。

### 2.2 StudyFetch

可借鉴点：

- 将学习资料拆成可逐步推进的主题；
- 将“已经覆盖”和“需要继续学习”显式呈现；
- 学习计划的价值主要体现在让用户更容易知道下一步做什么，而不是展示一个复杂计划本身；
- 学习计划与导师、练习、测验等工具联动。

对 Nautilus 的启发：

- 用户创建目标后，应尽快进入第一步行动；
- 计划的主要价值应是降低下一步决策成本，而不是要求用户维护复杂计划结构；
- 后续推荐应尽量落到具体行动，而不是泛化为“继续学习这个主题”。

边界：

- “covered / 已覆盖”不能自动等同于 Nautilus 的证据支持或稳定掌握；
- 外部产品的“mastered”定义不可直接映射到 Nautilus 的长期学习状态。

### 2.3 Brilliant / Koji

可借鉴点：

- Tutor 能看到用户当前正在处理的内容和已进行的操作；
- 在用户卡住时分步引导，而不是立即给完整答案；
- 将帮助嵌入具体学习环境，而不是让用户切换到脱离上下文的通用聊天；
- 交互式学习对象能产生比纯文本解释更直接的反馈。

对 Nautilus 的启发：

- 现有分步教学可以继续向“帮助阶梯”发展；
- 当用户卡住时，优先定位具体卡点，而不是重复整段知识；
- 对首个窄领域，可以考虑小型、可验证的交互练习组件，而不是优先建设通用白板或任意执行平台。

边界：

- 不把“永远不直接给答案”固化成规则；如果用户明确要求完整解释，教学场景应可以遵从；
- 教学中的理解确认仍不等于正式验证；
- 交互组件的结果只能证明其实际覆盖的范围，不能自动外推为泛化能力。

### 2.4 ChatGPT Study Mode / Khanmigo

可借鉴点：

- 分步解释；
- 先提问或检查理解，再继续；
- 根据用户反馈调整讲解方式；
- 将大问题拆成较小的学习步骤。

对 Nautilus 的候选建议：

可以将当前分步教学进一步收敛为几种自然帮助动作，例如：

- 给一点提示；
- 换一个例子；
- 只解释这一步；
- 让我自己试；
- 直接完整讲解。

这些动作不一定需要做成永久按钮，也可以由上下文动态出现。

特别值得保留的记录：

- 用户在本产品内是否已经看过提示、示范或参考解法；
- 本次尝试是在什么帮助条件下产生的。

边界：

- “没有记录到帮助”不等于用户现实中完全没有外部帮助；
- 不补造旧记录中不存在的帮助历史；
- 已保存验证结果不能因为后续教学或讨论被偷偷改写。

### 2.5 ALEKS

可借鉴点：

- 通过 Knowledge Check 区分“已知、未知、当前适合学习”的内容；
- 后续评估如果发现之前学过的内容没有保持，会重新进入学习路径；
- 下一步学习由当前状态驱动，而不是机械按照固定目录推进。

对 Nautilus 最有价值的启发：

> 一次反馈的终点不应该只是“给出评价”，而应该能够生成一个与当前缺口直接相关的下一步行动。

候选例子：

| 当前观察 | 候选下一步 |
| --- | --- |
| 概念解释含混 | 用自己的话重新区分两个相近概念 |
| 当前样例正确但边界不清楚 | 换一个边界条件不同的新例子 |
| 在提示后答对 | 安排一个不预先展示提示的新任务 |
| 推理过程缺失 | 补充关键一步及理由 |
| 用户质疑 AI 判断 | 先复核原题、原答和依据，而不是继续加题 |

边界：

- 重做原题和处理新情境不是同一类证据；
- 一次补练成功不等于稳定掌握；
- 没有合格标准时，可以保存练习和反馈，但不能让模型自行创造正式能力状态。

### 2.6 RemNote / Anki

可借鉴点：

- 学习材料与复习对象保持关联；
- 系统会考虑“什么时候复习”以及“复习负担”；
- RemNote 的考试计划会把需要练习的对象重新组织成每日可执行负载；
- Anki FSRS 明确处理期望保持率和复习工作量之间的权衡。

对 Nautilus 的候选建议：

优先考虑轻量“待回访”机制，而不是先做完整背卡系统。

每个回访至少应能解释：

1. 复查什么；
2. 为什么现在需要复查；
3. 建议用什么方式复查。

例如：

> 当前只有即时作答记录，尚没有延迟后的表现。后续可用一个新问题检查用户是否仍能解释该概念。

回访形式应与待验证的维度匹配：

- 记忆：不看原文回忆；
- 理解：解释原因或区分相近概念；
- 运用：完成一个新的具体任务。

边界：

- 不建议默认生成大量卡片和无限增长的复习队列；
- “安排回访”不等于“已经完成回访”；
- 未按时复习不等于能力失败；
- Anki/RemNote 的记忆调度模型不能直接当作跨领域能力掌握模型。

### 2.7 Gemini Notebook（原 NotebookLM 产品线）

可借鉴点：

- 用户可以明确选择本次对话应使用哪些来源；
- 回答引用能定位回原始来源内容；
- 可以从来源生成测验、抽认卡等学习材料；
- 网络或文件搜索得到的候选来源，需要被选择后才进入当前 Notebook 的来源范围。

对 Nautilus 的候选建议：

如果继续推进既有 `FOLLOWUP-SEARCH-001`，可以优先考虑下面的最小可信流程：

```
发现学习缺口
  -> 提出有范围的检索需求
  -> 实际执行检索
  -> 展示候选来源
  -> 用户选择纳入
  -> 基于已选来源继续学习
```

需要明确区分：

- 搜索到了某个来源；
- 实际查看了某个来源；
- 当前回答实际使用了某个来源。

不能因为模型生成了 URL 或自称“已经搜索”，就展示为真实联网核验。

边界：

- 资料中的知识不是用户掌握该知识的证据；
- 外部资料、AI 生成内容、用户原始产出应保持不同身份；
- 搜索结果不能自动升级为已审核达成标准；
- 不建议为了模仿 Gemini Notebook 立即扩大到完整 PDF/Word/图片工作台、向量库或全局知识库。

### 2.8 ForeverLM 等“复习会话 + 历史记录”产品

可借鉴点：

- 让用户先自行复述，再由 AI 追问薄弱点；
- 保存复习摘要和历史会话；
- 学习记录不是孤立聊天，而是围绕持续复习对象组织。

对 Nautilus 的候选建议：

可以围绕一个可验证成果提供轻量“学习依据”视图，回答：

- 当前有什么依据？
- 哪些内容仍不能说明？
- 最近一次实际产出是什么？
- 当时使用了什么帮助或资料？
- 哪个判断曾被质疑？
- 下一次还需要什么样的新表现？

优先复用已有原始产出、事实事件、评估版本和证据引用，不再复制一套“学习档案数据”。

边界：

- AI 生成的整体评分或总结不应直接成为 Nautilus 的长期学习状态；
- “存在一段复习对话”不等于“复习通过”或“稳定掌握”。

## 3. 值得优先讨论的七组候选方向

> 下列顺序仅表示本次调研中观察到的潜在产品价值，**不是已确认优先级，也不是开发顺序**。

### 3.1 返回卡：恢复位置 + 推荐理由

当前 Nautilus 已经有返回连续性的基础能力。相比新增更复杂的推荐 Agent，更值得优先讨论的是是否把已有推荐理由真正呈现给用户。

候选结构：

- 上次做到哪里；
- 已有事实或依据；
- 当前未知；
- 一个建议动作；
- 为什么建议它；
- 继续 / 换一个 / 今天先停。

核心思路：

```
历史事实 -> 尚未解决的问题 -> 一个行动 -> 行动理由
```

### 3.2 学习室：轻量“本次学习”结构

候选最小信息：

- 本次要解决什么；
- 当前环节；
- 完成本次学习前还剩什么。

目的不是增加课程管理，而是让聊天之外仍有稳定的位置感。

### 3.3 帮助阶梯

在现有分步教学上增加更自然的帮助级别控制：

- 小提示；
- 换例子；
- 解释当前步骤；
- 用户自己尝试；
- 用户主动要求完整讲解。

同时记录本产品内明确发生的帮助条件。

### 3.4 逐题反馈 -> 一个补练行动

相比继续丰富反馈文字，优先讨论是否让每条重要反馈能转成一个具体、可确认的后续练习。

建议保持“一次只给一个最相关行动”，避免自动生成大量练习。

### 3.5 轻量延迟回访

围绕一个具体成果和一个明确缺口安排后续复核。

第一版不需要通用背卡、不需要复杂遗忘曲线 UI，也不需要全局复习日历。

### 3.6 任务范围内的来源选择

如果启用联网搜索或资料输入，优先保证：

- 来源范围明确；
- 用户能看见来源；
- AI 实际使用的来源可以追溯；
- 私密内容不会被无边界带出任务。

### 3.7 一个成果的“依据回看”

先把一个成果的事实、产出、反馈、质疑和后续回访讲清楚，再决定是否需要完整成果图、知识图谱或路径图。

## 4. 当前不建议因为竞品存在就自动扩张的方向

以下功能并非永远不做，而是本次调研不足以证明现在就应该进入开发：

- 完整课程生成平台；
- 通用知识图谱；
- 全局向量知识库；
- 大规模 PDF / Word / 图片学习工作台；
- 自动批量生成闪卡；
- 完整遗忘曲线调度系统；
- 音频总结作为核心产品能力；
- 主动后台教练；
- 通用白板；
- 任意代码/工具执行沙箱；
- 多 Agent 并行学习编排；
- 插件/知识包市场；
- 复杂学习积分、等级或游戏化体系。

这些能力可能在未来有价值，但不应仅因为竞品已有类似功能，就被解释为 Nautilus 的必备项。

## 5. 与 Nautilus 当前差异化的关系

本次调研的一个重要观察是：

> “AI 导师 + 个性化路径 + 资料问答 + 练习生成”本身已经是较常见的组合，不能单独构成 Nautilus 的长期差异化。

Nautilus 更值得继续验证的差异化是：

1. **结论可解释**：为什么系统认为当前需要做这一步；
2. **依据可追溯**：判断来自哪一次真实产出、事实或来源；
3. **历史不覆盖**：后续学习、重试、质疑不会改写过去发生的事实；
4. **状态有边界**：一次答对、一次 AI 评价或一次自报不能自动升级为稳定掌握；
5. **中断可恢复**：用户回来时不需要重新理解整个项目；
6. **下一步可行动**：系统不仅指出问题，还能给出一个合理、可拒绝、可更换的下一步。

## 6. 建议的产品验证方式

如果后续需要继续比较竞品或验证 Nautilus，可以尽量使用同一条真实学习任务，而不是比较功能数量。

建议测试脚本：

1. 提出一个不够清晰的学习目标；
2. 开始第一次学习；
3. 完成一次真实作答；
4. 暴露一个具体错误或薄弱点；
5. 中断学习；
6. 隔一段时间回来；
7. 继续补练；
8. 用一个新情境重新验证。

观察：

- 起点是否容易确定；
- 用户是否知道当前在做什么；
- 帮助是否过量或过早；
- 错误是否真正转成下一步行动；
- 中断后是否恢复到正确位置；
- 新的判断是否能回到真实作答和来源；
- 后续尝试是否被错误合并或重复计数；
- 产品是否把“做过”误当成“掌握”。

## 7. 候选讨论顺序（非路线图）

> 这一节只用于未来产品讨论，不代表已批准排期。

如果未来要从本次调研中选择少量方向继续验证，可以优先讨论：

1. 是否先把返回卡已有的推荐理由和恢复位置做得更清楚；
2. 是否给学习室增加轻量的当前环节/完成条件；
3. 是否让逐题反馈直接产生一个可确认的针对性补练；
4. 是否在现有分步教学上加入最小帮助阶梯；
5. 是否在已有 `FOLLOWUP-SEARCH-001` 范围内采用“检索 -> 选择来源 -> 使用来源”的可信流程；
6. 是否在一个有合格标准的窄领域试验延迟回访；
7. 是否先做单成果的依据回看，再决定是否值得做完整成果图或路径图。

再次强调：**以上顺序不是开发任务顺序。** 当前安全修复、已确认工作项、真实使用基线和其他正式优先级仍以权威文档为准。

## 9. 后续使用规则

未来 Agent 阅读本文时应遵守：

- 不把本文任何建议标记为“已确认”；
- 不因为本文列出某功能就自行创建开发任务；
- 不因为“竞品已有”就假设 Nautilus 必须实现；
- 不用本文覆盖 PRD、产品决定记录或开发状态；
- 如需要采用某项建议，应先核对当前正式文档和代码事实；
- 涉及明显产品取舍时，应由产品负责人确认；
- 一旦某项建议正式确认，应把确认结果写入正式权威文档，而不是反向把整篇研究文档升级成规范。

本文的作用是保存可复用的市场观察和设计启发，而不是扩大产品范围。
